# Technical Decision Log

Format: ID, date, decision, rationale, alternatives. Append new decisions at the end.

## D001 Go 1.27.3, module github.com/sHyanorn/recserve, MIT
- Date: 2026-11-08
- Decision: go.mod says `go 1.27.3`, the latest release on go.dev/dl (2026-10-19). The module path is `github.com/sHyanorn/recserve`; the license is MIT
- Rationale: Go supports each major release until two newer ones are out, so 1.27 and 1.26 are supported. grpc v1.85.0, client_golang v1.25.0 and otel v1.47.0 all require Go 1.26 or later in their go.mod
- Alternatives: Go 1.26 (supported, but the toolchain the sister project matching-engine already uses is 1.27.3)

## D002 HTTP/JSON outside, gRPC inside
- Date: 2026-11-08
- Decision: Clients call the gateway over HTTP/JSON. The gateway calls shards over gRPC (google.golang.org/grpc v1.85.0, Apache-2.0)
- Rationale: JSON is easy to call and to read in a demo. Between services, gRPC gives deadlines that propagate, cancellation, connection reuse, health checking and generated code; a shard answers with float32 scores (float64 since D040) and int32 IDs, which protobuf encodes compactly
- Alternatives: HTTP/JSON everywhere (deadline propagation and cancellation by hand); gRPC everywhere (harder to try from a browser or curl)

## D003 Two process kinds: gateway and annshard
- Date: 2026-11-08
- Decision: The gateway is stateless across requests and runs the whole request path; it keeps the feature store, co-occurrence table, popularity list and models in memory. annshard holds one shard of item vectors and answers nearest-neighbor queries. Ranking runs in the gateway process
- Rationale: Only vector search grows with the catalog and benefits from sharding. Features and co-occurrence for these datasets fit in memory, and a separate feature or ranking service would add a network hop to every request without showing anything new. Vespa splits stateless containers from stateful content nodes the same way
- Alternatives: a feature service and a ranking service (more hops, more processes to operate); one process with everything (no distribution to show)

## D004 A static cluster layout
- Date: 2026-11-08
- Decision: A config file lists shards and their replica addresses (a gateway flag since D040). The gateway health-checks replicas, retries another replica on failure and hedges slow requests. There is no consensus, automatic resharding or dynamic membership
- Rationale: Failover, partial results and hedging are what a request sees; membership changes are an operations feature that needs a consensus store to do right, and doing it halfway would be worse than leaving it out
- Alternatives: etcd-based membership (a dependency and a failure mode of its own for a 4-replica layout)

## D005 Server-side p99 of 50 ms; headline is the highest rate meeting it
- Date: 2026-11-08
- Decision: The service target is a server-side end-to-end p99 of 50 ms, split by stage as in SPEC §5. The headline result is the highest offered rate at which all three runs are valid and have p99 ≤ 50 ms
- Rationale: A latency figure without its load, or a throughput figure without its latency, says little. 50 ms leaves room for a client-facing budget of the usual 100 to 200 ms
- Alternatives: maximum throughput alone (ignores the tail); a fixed throughput target (unknown before measuring on this hardware)
- Amended in M6 (D054): each run also has at most 1% of its responses degraded

## D006 ONNX Runtime through onnxruntime_go
- Date: 2026-11-08
- Decision: Models run with ONNX Runtime 1.31.x (MIT) through `github.com/yalue/onnxruntime_go` v1.38.0 (MIT), which uses cgo and loads the shared library with dlopen. The binding is built against the 1.31.0 C API, so the library version is pinned to 1.31.x. This stands only if the M0 check (docs/BENCHMARKS.md, M0) passes; otherwise the fallback named there applies
- Rationale: ONNX is the exchange format seqrec-lab can export from PyTorch, and ONNX Runtime is the reference runtime for it. Twitter's navi also serves its home ranker through ONNX. Pure-Go ONNX runtimes are experimental (owulveryck/onnx-go) or unmaintained (gorgonia, no commits since 2023-10)
- Alternatives: a separate inference server (a network hop per request); pure-Go inference written by hand (fine for a small MLP, a lot of work for a Transformer encoder)

## D009 An open-loop load generator of our own, on separate CPUs
- Date: 2026-11-08
- Decision: `cmd/loadgen` sends request i at t0 + i/rate whatever the replies and measures latency from that due time, as matching-engine's D030 does. Percentiles are exact, from sorted samples. During benchmarks loadgen and the services run on disjoint CPUs (taskset). vegeta cross-checks one rate
- Rationale: Closed-loop generators wait for replies and hide stalls (wrk2 README; Schroeder et al., NSDI 2006). ghz runs closed-loop unless `--async` and measures from the actual send; k6 is AGPL and adds a JavaScript runtime. Our generator needs dataset-driven request bodies and per-response checks (arm, versions, degraded reasons), which off-the-shelf tools do not do
- Alternatives: vegeta alone (no per-response checks); wrk2 (Lua scripting, HTTP/1 only)

## D010 Model bundle contract
- Date: 2026-11-08
- Decision: seqrec-lab exports the bundle described in SPEC §8: manifest, item ID list, item vectors as `.npy`, user encoder in ONNX, optional ranker, golden cases. The service verifies checksums and golden outputs before a swap

## D014 Every benchmark run is bracketed by a noise baseline
- Date: 2026-11-08
- Decision: Before and after each benchmark run a fixed single-core workload is timed (docs/BENCHMARKS.md, Noise baseline). A run whose baseline is more than 10% slower than the session reference is flagged and rerun, at most twice; a run still flagged is reported as such
- Rationale: Cloud VMs share CPUs with other tenants; matching-engine saw stalls of up to 128 ms with no engine code running. A baseline measured around each run separates a slower machine from a slower service
- Alternatives: hiccup meter only (catches stalls, not a slower CPU share)

## D015 ONNX Runtime sessions run with one intra-op thread
- Date: 2026-11-09
- Decision: R1 passed (docs/BENCHMARKS.md, Results), so D006 stands. Every session is created with intra-op threads = 1; concurrency comes from goroutines sharing a session, bounded by the service's concurrency limit
- Rationale: At concurrency 4 on 4 CPUs, the default thread pool raised p99 by 2.7 to 8.3 times over one intra-op thread, because each call's worker threads compete with the other callers
- Alternatives: the default pool (faster single calls for the L = 200 encoder, worse under load)

## D016 HNSW written by hand
- Date: 2026-11-09
- Decision: R2 failed, so D007's fallback applies: M2 implements HNSW (Malkov and Yashunin) in the service, with vectors in one float32 array, neighbor lists in flat int32 arrays per layer, beam search bounded by ef, and the neighbor-selection heuristic. It is measured in M2 with the R2 protocol unchanged, against the same exact and faiss baselines
- Rationale: coder/hnsw v0.6.1 reached recall@100 of at most 0.064 on both sets and both settings, the same at every ef, while faiss reached 1.000 on the synthetic set with the same settings. Its layer search keeps only k results, stops at the first expansion without improvement, and its heap evicts an arbitrary result. Upstream's untagged fix of the search (36cab60) levels off at recall@100 0.824 on the synthetic set with p99 21 ms at ef = 800, so the graph it builds is the limit too: neighbors are pruned by distance alone, without the selection heuristic
- Alternatives: upstream coder/hnsw at 36cab60 (untagged, fails the recall target); patch it further (search and graph construction both replaced); cgo to faiss (a second native library, rejected in D007); exact search only (enough for the 25.6k-item catalog, but leaves the 1M-scale tier without an index)

## D017 Measurement corrections after the first M0 results
- Date: 2026-11-09
- Decision: (1) The GC CPU fraction is no longer measured; GC is judged by stop-the-world pauses and cycle counts. (2) Medians are true medians (mean of the two middle values) for the noise baseline and its reference. (3) The baselines around faiss runs are checked against the reference like any other run. (4) A result file keeps the baselines of the reported attempt only. (5) coder/hnsw is built with `Ml = 1/M`, and its R2 runs are repeated under a new session reference
- Rationale: (1) The runtime updates `/cpu/classes/*` only when a GC cycle ends, so over a query phase with zero or one cycle the fraction is 0 or covers the wrong interval. (2) The upper median was used by mistake; recomputing all committed baselines with the true median changes no flag. (3) Those baselines were recorded but not compared. (4) That is what the code does; the protocol text said otherwise. (5) coder/hnsw's `Ml` is the probability of promoting a node one layer up, 1/M in the paper's terms; 1/ln M made about 15 layers instead of 6 and inflated build time and heap. None of these changes a pass criterion
- Alternatives: keep the first coder/hnsw results (build time and heap measured on a wrongly shaped graph)

## D018 Scope: event queue, Valkey, fault injection under load, kind
- Date: 2026-11-09
- Decision: Four items join Required (SPEC §2): events through a Kafka-protocol topic with an ingest consumer (D019); user histories and the result cache in Valkey (D020); fault injection during load tests (D021); deployment on kind with probes, an HPA and a zero-error rollout check (D022). Milestones become M1 to M7 (docs/TASKS.md), with a new M3 for the event pipeline and shared state. The estimated work grows by about 1.9 times the size of M1: M3 about 1, kind about 0.5, fault injection about 0.4
- Rationale: In-process histories tie a user to one gateway instance and are lost on restart, so the gateway cannot scale out or be replaced without losing state; a durable log decouples writes from the serving path and lets the consumer be restarted and replayed. Fault injection under load measures the degradation paths that the property tests only check for correctness. kind checks that probes, rollout and swaps behave as designed under an orchestrator
- Alternatives: keep histories in process (no shared state, no restart safety); a database instead of a log (writes on the serving path)

## D019 Apache Kafka in KRaft mode, franz-go client
- Date: 2026-11-09
- Decision: `apache/kafka:4.4.0`, one node, combined broker and controller (KRaft), heap capped at 1 GB, offsets topic replication 1. Client `github.com/twmb/franz-go` v1.22. The gateway produces with the idempotent producer (`acks=all`), keyed by user ID; topic `events` has 6 partitions. The ingest consumer group commits offsets manually, after an event batch is applied to Valkey. Delivery is at least once; applying an event is idempotent (D020), so redelivery is harmless. Exactly-once holds only inside Kafka and is not relied on
- Rationale: Keying by user keeps each user's events in order within a partition. Committing after the apply means a crash replays events instead of losing them. Redpanda's Community Edition is under the Business Source License and its dev-container mode skips fsync, which makes its figures incomparable. franz-go is pure Go and supports idempotent production and manual commits; confluent-kafka-go needs cgo and librdkafka; segmentio/kafka-go documents no idempotent producer
- Alternatives: Redpanda (license, fsync); NATS JetStream (not the Kafka protocol); Go channels in process (no durability)

## D020 Valkey for user histories and the result cache
- Date: 2026-11-09
- Decision: `valkey/valkey:9.1`, client `github.com/redis/go-redis/v9` (replaced by valkey-go, D038). Each user's history is a sorted set: member = item ID and event ID, score = event time (D033 has the layout); retention follows D023. Applying an event is one `ZADD`, so applying it twice changes nothing. Feature lookup reads the members with score below the request time, so late or reordered events still respect property 1. The result cache key holds the index version, model version, arm, user, k and the ID of the user's latest event, with a TTL plus jitter; a swap or a new event changes the key, and old entries expire. Misses are computed once per key per instance with `golang.org/x/sync/singleflight`. Item features stay in the gateway. If Valkey fails or times out, a circuit breaker opens: requests use the `recent` items they carry, report `history_unavailable`, and skip the cache in both directions
- Rationale: Shared per-user state lets any instance serve any user. Item features are part of the bundle and immutable per version; a request reads about 500 of them, which in Valkey would add a 500-key read to every request. Redis 7.4 and later is under RSALv2/SSPLv1 (and AGPLv3 from 8.0); Valkey is BSD-3-Clause. go-redis does not list Valkey as supported, so the integration tests run against Valkey itself. Cross-instance duplicate computation is bounded by the number of instances, so no distributed lock is added
- Alternatives: Redis 8 (license); item features in Valkey (a 500-key read per request); a distributed lock against stampedes (another failure mode for a bounded saving); probabilistic early refresh (Vattani et al., VLDB 2015; worth it only for long, expensive recomputations)

## D021 Fault injection with toxiproxy and container control
- Date: 2026-11-09
- Decision: In the compose benchmark setup, toxiproxy (v2.13) sits between the gateway and each shard replica and Valkey; faults are added through its HTTP API. Faults: a shard replica killed (`docker kill`), latency on one shard (toxiproxy `latency`), Valkey unavailable (proxy disabled), the ingest consumer stalled (`docker pause`); from D041, a replica silent with its connection up (`docker pause`) and a replica that answers keepalive pings while its searches hang (`cmd/faultshard`, D052). ## D022 kind for deployment checks
- Date: 2026-11-09
- Decision: kind v0.33 (Kubernetes 1.37) with plain manifests and kustomize. metrics-server for the HPA, started with `--kubelet-insecure-tls`, which is for test clusters only. Liveness checks the process; readiness checks that a bundle is active and the instance is not draining. Deployments roll with `maxUnavailable: 0`, `maxSurge: 1`; on SIGTERM an instance fails readiness, waits in `preStop` for endpoint removal, drains requests, and the consumer commits its offsets. ## D023 Baseline bundle contract and full history retention
- Date: 2026-11-09
- Decision: (1) The bundle contract (SPEC §8) gains `user_encoder: mean`, a zero padding row 0 in `items.npy`, optional `cooc_ids.npy`, `cooc_counts.npy` and `popular.npy`, and drops `opset` and the input and output names until an ONNX encoder is exported. Golden cases need a history, a full user vector and exactly 10 IDs, and include histories longer than `max_seq_len`. The version is a hash of every file. ALS is trained on the train split's users and items only; items seen only later get zero vectors, and a user vector that is zero counts as absent. (2) User histories keep every event: the cap of 200 is dropped. Requests read the whole history before their time for the seen filter and the last `max_seq_len` items for the user vector
- Rationale: (1) An ONNX user encoder comes from seqrec-lab later; the baseline needs the same file layout without it. With the item set of all splits in the ALS input, the test split changed every trained vector through the random initialization. (2) Evicting old events made the seen filter miss items a user had rated and made earlier request times lose events; the property tests applied the same cap to their reference, so they could not see it. The full history of Video_Games fits in memory; M3 decides retention in Valkey without weakening properties 1 and 2
- Alternatives: keep the cap and a separate unbounded seen set (two structures to keep consistent); per-user time windows (loses old seen items)

## D024 Hand-written HNSW: what follows the paper, hnswlib and faiss
- Date: 2026-11-09
- Decision: `internal/hnsw` implements Algorithms 1, 2, 4 and 5 of Malkov and Yashunin (arXiv:1603.09320). Sources read: the paper; hnswlib `hnswalg.h` at commit ca42672 (the reference implementation, by the paper's first author); faiss v1.15.1 `impl/HNSW.cpp`, `impl/HNSW.h` and `IndexHNSW.cpp` (the outside reference of R2). The choices, fixed before any measurement:
  1. Parameters as the paper recommends and hnswlib uses: level multiplier mL = 1/ln M, at most M links per node on layers 1 and up, at most Mmax0 = 2M on layer 0; queries search layer 0 with max(ef, k)
  2. A new node selects M neighbors on every layer it lives on (paper, Algorithm 1; hnswlib). faiss selects up to its layer's maximum, 2M on layer 0
  3. Neighbor selection is the heuristic of Algorithm 4, always, also when there are fewer candidates than the target; hnswlib and faiss keep every candidate unpruned in that case. This differs only on layers, or early in the build, where fewer than M nodes are reachable
  4. A candidate is rejected when an already selected neighbor is strictly closer to it than the new node is; ties keep it (hnswlib, faiss). The paper's wording would reject ties
  5. When a link overflows a node's list, the node selects again with the same heuristic from its old neighbors plus the new one, down to the maximum (paper, Algorithm 1; hnswlib). faiss v1.15.1 prunes to 80% of the maximum (`prune_headroom` 0.2)
  6. The search on the next layer down starts from all nodes found on the layer above (paper, Algorithm 1: ep ← W). hnswlib starts from the closest selected neighbor only; faiss from the one node found by the greedy descent
  7. The paper's options `extendCandidates` and `keepPrunedConnections` are off, as in hnswlib; faiss's `keep_max_size_level0` is off by default
  8. Layer search follows Algorithm 2 with hnswlib's stopping rule: stop when the nearest unexpanded candidate is farther than the farthest result and the result set is full. A filter, as hnswlib's `isIdAllowed` and faiss's `IDSelector`, keeps nodes out of the results but not out of the traversal
  9. Visited nodes are marked in a per-searcher array of epoch tags, so it is not cleared between searches (hnswlib's visited list pool)
  10. Levels are drawn up front from a seeded generator and nodes are inserted in ID order, so a single-threaded build is reproducible. The parallel build follows hnswlib: one lock per node, held while its neighbor lists are read or written during the build, and a global lock while a node above the current top level is inserted. faiss v1.15.1 builds differently: points bucketed by level and inserted in prefix-doubling batches against a frozen snapshot, reverse links merged afterwards (after ParlayANN)
  11. Similarity is the float32 inner product (`vec.Dot32`), the distance its negative; on L2-normalized vectors the order equals cosine. faiss runs `METRIC_INNER_PRODUCT`
  12. Layout without pointers (D016): vectors are the caller's float32 array, unchanged; layer-0 links are one int32 array with 1 + 2M slots per node, the first holding the count; links of layers 1 and up are one int32 array with M + 1 slots per node and layer, found through a per-node offset; levels are bytes
- Rationale: The paper fixes the algorithm and hnswlib is its reference implementation; where they differ, the index follows the paper, and only in points 3 and 6, where the paper is explicit. faiss is the outside reference of R2, so its differences (points 2, 5, 10) are recorded here before results, as possible reasons for different recall at equal settings
- Alternatives: port faiss's batch build (reproducible in parallel, but a larger graph builder and not the classic algorithm); `keepPrunedConnections` (fills lists to the maximum; off in both reference implementations)

## D025 Noise baselines come from one noisebase build
- Date: 2026-11-09
- Decision: From M2 on, the session reference and every noise baseline are taken by running the same `cmd/noisebase` binary, pinned to the CPU named; benchmark commands run it as a subprocess instead of timing the workload in their own process, and result files record the binary's SHA-256. A reference is compared with another session's only if both come from builds of the same commit and toolchain; Go builds are reproducible, so an earlier build can be recreated from its commit
- Rationale: The workload's speed depends on where the linker places its inner loop. On the M2 machine, builds with identical loop instructions measured about 480,000 or about 590,000 ns per pass: in the faster ones the 34-byte loop lies inside one 64-byte line, in the slower ones it straddles two. Two builds that differ only in an unrelated import, one of each kind, were timed alternately six times, and the straddling one was slower every time. In M0 the reference came from `experiments/m0/cmd/noise`, whose loop straddles, while the R2 command, as built from b334c91 for the coder/hnsw rerun, timed its baselines in its own process, whose loop does not; if the M0 machine behaves the same way, the R2 baselines read faster than the reference and understate the flags. The R2 verdict rests on recall and does not change
- Alternatives: the loop in assembly with fixed alignment (the same placement in every binary, but a different workload from M0 and assembly to maintain); baselines in the measured process (the placement differs between binaries)

## D026 ONNX user encoder: baseline graph, calls and checks
- Date: 2026-11-09
- Decision:
  1. `tools/bundle/build.py --encoder onnx` adds `user_encoder.onnx`, a graph built with `onnx.helper` (opset 17, IR version 8) that computes the same mean as `user_encoder: mean`: the item vectors gathered, summed over the sequence and divided by the number of non-padding IDs (at least 1). Its golden user vectors come from running it with ONNX Runtime in Python, so replaying them checks the encoder; the build fails if one differs from the float64 mean by more than 1e-5. The input and output names are fixed by SPEC §8 and the opset is the model's own, so the manifest gains no field; `build.user_encoder` records the graph, opset and library versions
  2. The service calls the encoder with B = 1 and L = `max_seq_len`, left-padded. The tensors and run options of a call come from a free list that keeps at most 64 idle calls; more are created when needed and destroyed after use
  3. A call whose context ends is stopped with `RunOptions.Terminate`, which ONNX Runtime checks between nodes; the error of a run it terminated wraps the context's error, and the flag is cleared before the call is reused. A run that fails for another reason while the context ends returns its own error, so a failing model is not reported as a timeout; ONNX Runtime tells a terminated run apart only by its message, "Exiting due to terminate flag being set to true"
  4. Closing an encoder waits for running calls, and later calls fail with `ErrClosed`. Reference counting at bundle swaps decides when to close (M2, two-phase swap); this only turns a misuse into an error
  5. Go and Python ONNX Runtime on the same machine must agree within 1e-5: the real-data test compares the golden user vectors of a bundle built on the machine it runs on (measured difference 0). Loading accepts 1e-4, for bundles built on another CPU
  6. CI downloads ONNX Runtime 1.31.1, checks its SHA-256 and sets `RECSERVE_REQUIRE_ORT`, which turns the skip of tests that need the library into a failure. The test models are written by `tools/bundle/testdata.py` with the same graph builder, and the tests check them against a committed SHA256SUMS
- Rationale: A graph whose output is known exactly tests the ONNX path end to end before seqrec-lab exports a sequence encoder, and the same bundle can be built either way for comparison. ONNX tensors wrap C-side values that must be released, so a pool that drops values silently (`sync.Pool`) does not fit. A run abandoned in its goroutine would keep a CPU busy after its deadline; Terminate frees it within one node
- Alternatives: export the mean from PyTorch (a large dependency for four operators); new tensors for every call (a C allocation and release per request); test models built in Go (a second graph builder besides the one in `build.py`)

## D027 Ranker contract: fixed rows, six features, fallback to retrieval order
- Date: 2026-11-09
- Decision:
  1. `ranker.onnx` takes `features` float32 [C, F] and returns `score` float32 [C]; the manifest's `ranker_features` names the columns and must equal the six the service computes (SPEC §8, Ranker features), in order. The baseline bundle has no ranker; `make bundle RANKER=1` adds the logistic regression of point 7
  2. Every call passes C = 512 rows (`bundle.RankerRows`), the rows past the candidates set to zero. When there are more candidates, the 512 with the highest retrieval scores are ranked and the rest dropped; the gateway counts truncated requests and dropped candidates (`recserve_ranker_truncated_requests_total`, `recserve_ranker_candidates_dropped_total`). Without a ranker nothing is dropped
  3. A ranker's scores must depend on their own row only. Loading checks it: the ranker runs on 512 zero rows, then with row 0 set to fixed values, then with rows 1, 256 and 511 set to fixed values instead, and every row left at zero must score the same as in the first run, bit for bit; it must also return 512 finite scores. `tools/bundle/verify.py` applies the same check. A ranker that adds the next row's score to each row passes a change of row 0 alone, and fails the second (`next_row_ranker.onnx`)
  4. Every feature uses only the history before the request time and the bundle, is computed in float64 and rounded to float32, so the Python trainer can reproduce it
  5. The ranker's score replaces the retrieval score. MMR already scales scores to [0, 1] over the candidates, so the ranker's range and scale are free; only their order matters to it. If the ranker times out or fails, the retrieval scores are kept and the response reports `ranker_timeout` or `ranker_error`; a request cancelled by its client fails instead
  6. `onnx.Ranker` shares the encoder's call path: tensors and run options from the free list, `Terminate` on a context's end, `ErrClosed` after Close
  7. The ranker is a logistic regression (scikit-learn 1.9.1, L2, C = 1) trained in `tools/bundle/build.py --ranker` on the valid split: a request at each valid user's first valid event, whose history is the user's train events, has the service's candidates, the 512 best of the vector top 200, the co-occurring and the popular items without the seen ones, labelled 1 where the user has a valid event on the item. The co-occurrence table, the popularity list and the item vectors that the features read are built from the train split alone, which ends before the valid split starts (the build checks it), so no label leaks into a feature. Users none of whose valid items are candidates are left out; 20% of the rest are held out. The features are standardized for the solver and the scaling folded into the weights, so `ranker.onnx` is the MatMul and Add graph of `linear_ranker`, its score the logit. `train_cutoff_ts` becomes the valid split's last event, still before the test split's first. On the Video_Games bundle b7ff0634dd7b (ONNX encoder): 3,402 of 14,239 valid users had a valid item among their candidates; on the 680 held out, recall@10 0.091 by the ranker against 0.026 by retrieval score, and mean per-user AUC 0.726 against 0.388, both before MMR. The weight of `vector_score` is negative: among the candidates, the items a user went on to choose came more from co-occurrence and popularity than from the vector score
  8. With a ranker every golden case carries its candidates and their features, computed by the same Python code that computed the training features. Loading recomputes them with the service's code from the case's history and user vector and rejects the bundle if any differs by more than 1e-6; `verify.py` does the same in Python. In CI the check runs on `ranker_golden.jsonl`, written by `tools/bundle/testdata.py` for the test bundle; the broken variant, `log_history_len` computed as ln |H| in Go, made the real bundle fail to load (checked once, by hand)
- Rationale: Fixed rows keep the free list of D026: a call's tensors are allocated once, and ONNX Runtime plans memory for one input shape. The cost is ranking padding rows, small for a linear model or a small MLP over six features; on the Video_Games bundle 12% of requests had more than 512 candidates (2,000 requests, at most 156 dropped; a one-off measurement whose code is not committed). Padding is safe only for a row-wise model, so the contract is checked rather than assumed. Features that Python can recompute exactly let the trainer's features be checked against the service's
- Limits: The trainer orders a user's train events at one time by internal item ID, the service by event ID, so for users whose latest events share a time, training saw another last item and other co-occurrence seeds than a request sees; the golden check gives both sides one history and cannot see it. The golden fixes the candidates, not how they are chosen: a change of the retrieval sizes on one side passes it. The CI golden has one co-occurrence seed with a non-empty row and no item reached twice, so a fault in combining several seeds shows only when a real bundle loads
- Alternatives: tensors sized per request (a C allocation and release per call); size buckets of 64 to 512 rows (less padding, a free list per bucket); a fixed output range for rankers (needless, given the min-max scaling in MMR)

## D028 In-process shards in M2, exact search by default
- Date: 2026-11-09
- Decision:
  1. Vector retrieval goes through shards from M2: the gateway splits the item vectors by `shard.Of` into two shards by default (`-shards`), each holding a contiguous copy of its vectors, and merges the shards' top k by score, then internal ID. Property 6 is tested on these shards, with a broken variant that asks each shard for ceil(k/n) items, and again through the pipeline's vector retrieval on catalogs larger than `VectorTop`, whose broken variant asks each shard for ceil(`VectorTop`/n). M4 moves the shards behind gRPC with replicas and keeps the merge
  2. Items whose vector is zero are left out of the shards. Their inner product with any query is 0, so whether they enter the vector results depends on the other items' scores and on their IDs, not on the query. They still come from co-occurrence and popularity. The Video_Games bundle has 2,636 of 25,612; on 2,000 real requests (every 20th test event, k = 50) leaving them out changed no response, with either bundle (a one-off comparison whose code is not committed)
  3. Each shard searches exactly by default (`-shard-mode exact`); HNSW (M = 16, efConstruction = 200, `-hnsw-ef`) is an option. An exact search checks its context every 1,024 rows; an HNSW search only before it starts
- Rationale: On the same 2,000 requests (1,348 with a user vector), on the 4-CPU M2 machine, the pipeline took p50 2.19 ms and p99 3.63 ms with one exact shard, and p50 1.42 ms and p99 2.46 ms with two, searched in parallel. The test runs each request on one shard, then immediately on two, so the two-shard run finds the request's history and co-occurrence rows in the CPU caches; the order favors two shards by an amount not measured. HNSW over the bundle's vectors, which are not normalized, so the search is maximum inner product, levels off below the recall target of docs/BENCHMARKS.md: recall@100 0.860, 0.865, 0.868 at ef 200, 400, 800 with one shard, and 0.930, 0.932, 0.941 with two (recall@200 0.73 to 0.84), at p99 0.65 to 0.99 ms against 1.9 to 3.1 ms for exact search. Recall barely grows with ef, so the graph, not the search list, is the limit. At 25.6k items exact search fits the 15 ms budget with room to spare
- Alternatives: exact search on one node until M4 (no partial results to degrade to in M2); HNSW by default (fails the recall target here); the transformation of Bachrach et al. (RecSys 2014), which appends sqrt(max‖x‖² − ‖x‖²) to each item so that inner product order becomes Euclidean order, a known remedy for graph search under inner product (Morozov and Babenko, NeurIPS 2018, discuss inner-product graphs directly); not done in M2, pending a decision

## D029 Per-stage deadlines and degradation
- Date: 2026-11-09
- Decision:
  1. Each stage of a request runs under a context with its own budget (SPEC §5; gateway flags `-budget-*`, 0 for none). A shard search's context derives from the retrieval context, so it ends at the earlier of the two deadlines. The sources of retrieval run in parallel, each shard in its own goroutine
  2. A stage's error is a timeout if it wraps `context.DeadlineExceeded`, otherwise an error, giving the `_timeout` or `_error` reason. The history lookup reports `history_unavailable` either way. Before classifying, the request's own context is checked: if it has ended, the request fails with an error that wraps it (499 when cancelled, 504 past the caller's deadline), so a caller's deadline is never reported as a stage's timeout
  3. Fallbacks: without the stored history, the request's `recent` items are the history, and they and `exclude` are the seen items; without a user vector, vector retrieval is skipped and candidates keep their source scores; a source that fails contributes nothing; shards that answered are merged as usual and `coverage` counts them, `shards_partial` if some did not, `vector_timeout` if every shard timed out, `vector_error` if none answered and one failed; a ranker that fails leaves the retrieval scores
  4. The request waits for every stage to return, also past its deadline; nothing it started keeps running after it returns. The stages check their context themselves: exact search every 1,024 rows, ONNX Runtime between nodes through `Terminate` (D026), an HNSW search only before it starts
  5. A response lists each reason once, in the order of SPEC §5. `recserve_degraded_total{reason}` counts responses by reason; an error other than a timeout is logged at warning level with the reason, and a timeout is only counted
  6. Tests make stages fail through an unexported hook on the pipeline, called at the start of each stage and shard search under the stage's context; in production it costs a nil check
  7. ONNX Runtime logging is left at the Go binding's default, the error level: a terminated run logs nothing at that level. The 1,992 runs of `slow_ranker.onnx` terminated in the real-data test printed nothing, and with the gateway serving the ONNX bundle at an encoder budget of 20 µs, 48 of 115 requests reported `encoder_timeout` and stderr held only the gateway's own lines
- Rationale: Waiting for stages keeps a request's resources its own until it returns: a bundle swap (M2) can release an old bundle once no request holds it, and no CPU keeps working for a request already answered. The cost is that a stage ends after its deadline by the time to its next context check, plus the delay of the deadline's timer. Measured on the 4-CPU M2 machine, over the 2,000 requests of the shard test (every 20th test event, k = 50), from a stage's deadline to the start of the next stage (to the response after ranking, so including MMR), on either bundle: with a hook that waits for the deadline of 1 ms, p50 0.18 to 0.42 ms and p99 0.35 to 1.02 ms by stage, max 12 ms; exact search with a shard budget of 100 µs, p50 0.66 to 0.93 ms and p99 1.38 to 1.44 ms; the ONNX encoder with budgets of 5 and 20 µs, p99 0.40 and 0.47 ms, and only 407 and 332 of 2,000 requests timed out, since a context's deadline takes effect when its timer fires; an ONNX ranker of 300 nodes (`slow_ranker.onnx`, 1.7 to 2.8 ms a run) at a quarter of its run, p50 0.85 to 1.10 ms and p99 1.24 to 1.56 ms. Budgets of 3 to 15 ms absorb these delays. With the default budgets no request degraded on either bundle, and with no budgets every response equals the one before this change, item by item (a one-off comparison whose code is not committed). Classifying by the error, not by which context ended, keeps a client library's own timeout (Valkey, M3) a timeout
- Alternatives: return at the deadline and leave the stage running (the request returns on time whatever the check interval, but it no longer knows when its bundle is free, and the stage keeps a CPU busy); classify by which context ended (a library's own timeout would count as an error); a reason per shard (coverage gives the count and the log names the shard)

## D030 In-process result cache keyed by version and history
- Date: 2026-11-09
- Decision:
  1. The key is the SHA-256 of a length-prefixed encoding of the bundle version, the user, k, the exclusions as a sorted set and the items of the user's history before the request time, in order. The request time is left out, since it acts only through the history; so are the `recent` items, used only when the history cannot be read, and such a request neither reads nor writes the cache. The key also holds the shard settings (D036 point 7) and the A/B arm, its name and mode (D049)
  2. Any server setting that changes a response that was not degraded must be in the key or fixed for the cache's life. Today the bundle is the only one that changes (two-phase swap, M2) and it is in the key; `-shards`, `-shard-mode` and `-hnsw-ef` are fixed at start. The budgets only decide whether a response degrades, and a degraded response is not cached, so they stay out
  3. Only responses that were not degraded are stored. A hit returns the stored response; its ranker truncation count is not counted again. `recserve_cache_lookups_total{result}` counts hits and misses
  4. `internal/cache` is a least-recently-used map of at most `-cache-size` entries (13,000 by default, 0 for none), one mutex; each entry lives for `-cache-ttl` (5 minutes) times a uniform factor in [0.9, 1.1], so entries written together expire apart, and an expired entry is dropped when read or evicted. The cache is shared by the pipelines of every bundle the gateway serves
  5. Size: on the 2,000 real requests with k = 100, the largest k, every response held 100 items and an entry took 3,062 to 3,069 bytes of heap over three runs, the cache's own map, list and entry included (100 items of 24 bytes take a 2,688-byte allocation; item IDs share the bundle's strings). 13,000 entries take at most 39.9 MB; at k = 50 an entry takes about 1.7 KB
- Rationale: The history is in the key, not the latest event before the request time, because property 8 allows an event to arrive after a later one: the history then changes while its latest event does not, and a key by the latest event would serve the response computed without the late event (a test sends one). Retention (D023) likewise changes the history's start, not its end. A full digest also spares a collision check: two requests share a key only if they would compute the same response. The cost is that a hit still reads the history; on the Video_Games bundle a hit took p50 2 µs and p99 4 to 6 µs, the in-process history read and the digest included, against p50 1.4 to 1.5 ms and p99 2.5 to 3.3 ms for a miss. With Valkey (M3) a hit reads the history over the network; a per-user history version would avoid that read and is left to M3. Of the 2,000 requests, 47 repeat an earlier one's user and history, so a cold cache already hits a few
- Alternatives: the latest event ID before the request time (stale after a late event, above); a 64-bit hash of the same fields (smaller, but a collision would serve another user's response); hashicorp/golang-lru (a dependency in place of about 100 lines, its expiring variant has one fixed lifetime, and the cache moves to Valkey in M3); compact entries of internal IDs and scores (about half the memory, at the cost of rebuilding the items on every hit)

## D031 Two-phase bundle swap in the gateway
- Date: 2026-11-09
- Decision:
  1. `recommend.Live` holds the active pipeline (bundle, shards, budgets, cache) and a reference count: one per request that holds it, plus one while it is active. A request takes a reference when it starts, with a compare-and-swap that refuses a count of zero (a retired version may already be closing; the pointer then names its successor), uses only that pipeline, and releases it when `Recommend` returns, after which nothing it started still runs (D029, point 4). `/v1/events` holds the active bundle only while it maps item IDs
  2. `POST /v1/admin/swap {"bundle": dir}` prepares while the active version serves: `bundle.Load` verifies checksums, golden cases and the train cutoff, then the shards are built with the gateway's start flags. A bundle whose version is active (409) or whose item IDs differ from the active bundle's (422) is rejected after loading, and so is one that fails to load (422); the rejected bundle is closed and the active one stays. Activation is one atomic store. The swap then drops the active reference to the previous version, waits until no request holds it and calls `Bundle.Close`, which closes its ONNX sessions; only then does it return, with the prepare and drain times
  3. One swap runs at a time; another gets 409 at once. The swap lock is held through the drain, so at most two bundles are in memory. The drain has no time limit, since a bundle in use must not be closed: a request ends within its budgets, but one run without budgets need not, and neither need a holder added later, so the swap logs a warning with the number of requests still holding the previous version every 5 s. Shutdown is bounded instead: the gateway waits at most `-drain` for requests in flight and, if some are still running, logs a warning and exits without closing the bundle. Once the bundle is closed, `/v1/recommend`, `/v1/events` and the swap answer 503
  4. The history store holds internal item IDs, mapped by the bundle active when an event arrived, so a swap requires the new bundle's `items.ids` to equal the active one's, item for item. M3 stores raw item IDs in Valkey and lifts this (TASKS, M3)
  5. `-shards`, `-shard-mode` and `-hnsw-ef` stay fixed for the process; a new version is indexed with them. The cache stays shared and keyed by version, so D030's key needs no change, and entries of a version swapped out and back in stay valid. This relies on a version naming its content: `tools/bundle` derives it from the hash of every file, and the loader checks it (D046)
  6. The admin API has its own listener, `-admin-addr`, 127.0.0.1:8081 by default and empty to turn it off; it has no authentication, and the gateway logs a warning when it listens beyond the loopback interface. `recserve_swaps_total{result}` counts swaps as ok, rejected or busy
  7. Property 4 runs eight workers against 200 swaps between two synthetic bundles with the same items and different vectors, co-occurrence and popularity, through a shared cache; every response must equal, item for item and score for score, the response of the version it names, computed by a pipeline that is never swapped. The broken variant scores candidates with the bundle active when scoring starts; a test hook holds the first request that reaches vector retrieval until a swap has activated the other version, so one request always scores across a swap. A second broken variant, with ONNX rankers, releases a request's reference as soon as it takes it: the held request's bundle is then closed under it and its ranker returns `onnx.ErrClosed`. Failed swaps are tested through the gateway's own prepare function with bundles that fail each check
- Measured in M6 (docs/BENCHMARKS.md, M6, bundle swaps): at 275 requests/s with nine swaps per run, a swap's prepare took 65 to 864 ms and its drain at most 3 ms. The seconds with a swap have a higher p99 than the others (6.5 to 11.3 against 5.2 to 6.3 ms) and no higher maximum, with GC on or off; their cause is not established
- Rationale: The reference count lets a request run lock-free on its version while a swap waits for exactly the requests that started before it; a read-write lock would serve as well but makes every request share the lock's reader count with the swap's writer. Waiting for the drain inside the swap keeps the number of bundles in memory at two and leaves no closing in the background to lose track of. Measured on the 4-CPU M2 machine with the two real bundles (5de55036a382 and 9fb3c7e84140, the same items) and the 2,000 real requests of D028, no budgets and no cache, 20 swaps under four workers: prepare p50 127 ms and max 233 ms, drain p50 1.4 ms and max 3.4 ms; request latency p50 1.85 ms and p99 3.4 ms without swaps, p50 1.99 ms and p99 15.2 ms (max 37 ms) during them, every response equal to its version's. After each request a worker computes the reference response on the same thread, so the CPUs carry about twice the timed requests' load: the comparison with and without swaps holds, the absolute latencies read high. Four workers already fill the four CPUs, and prepare competes with them: with three workers p99 went from 2.5 to 2.7 ms without swaps to 4.0 to 4.2 ms during them, max 23 to 35 ms (the test fixes four workers; the three-worker runs and the following gateway figure are one-off measurements whose code is not committed). The gateway at start and swapping once took 130 ms to prepare
- Alternatives: close the previous bundle in the background after activation (the swap returns sooner, but swaps could pile up bundles and a failed close would surface nowhere); a hard drain timeout that closes anyway (would break requests in flight); remap the history on a swap with different item IDs (the store moves to Valkey in M3, where raw IDs remove the need); allow `-shards` and the HNSW settings to change per swap (they would have to join the cache key, D030 point 2)

## D032 Histories hold raw item IDs
- Date: 2026-11-10
- Decision:
  1. `history.Event.Item` and `Store.Before` carry raw item IDs. A request maps its history to the internal IDs of the bundle it runs on right after reading it, leaving out the items that bundle does not know, as it does for `recent`. Seen items, the user vector, the ranker features and the cache key use the internal IDs as before; the cache key holds the bundle version, so two versions never share an entry
  2. `/v1/events` and `-preload` store every event, also for an item the active bundle does not know. `/v1/events` no longer reads the active bundle: it answers `{"accepted": n}` without `unknown_items`, and still answers after the bundle is closed at shutdown, as long as its producer does (D034; D031 point 3 counted it among the routes that answer 503)
  3. A swap accepts a bundle with other items; D031 point 4 and its 422 no longer apply. Property 4, and property 2 across a swap, run between two bundles of 40 items that share 35 under different internal IDs
- Rationale: A stored history outlives a bundle, and from M3 it lives in Valkey, read by gateways that hold different versions while a swap rolls out; an internal ID means something in one bundle only. Mapping when a request reads the history costs one map lookup per history item. Storing events for unknown items keeps the store independent of which version a gateway holds, and an item that the next bundle adds already has its events; the cost is that a mistyped item ID is stored and never used
- Alternatives: remap the stored histories on each swap (needs the items both bundles know and a pause in appends, and cannot work once several gateways share the store); keep dropping events for items the active bundle does not know (the answer would depend on the gateway's version, and events for an item not yet in a bundle would be lost)

## D033 Valkey history store: data model and retention
- Date: 2026-11-10
- Decision:
  1. `history.Valkey` implements `history.Store` on one Valkey server. A user's history is the sorted set `h:<user>`; an event is one member, its ID as 16 lowercase hex digits followed by the raw item ID, scored by the event time in milliseconds. An append is `ZADD NX`, one command per user and at most 1,000 events each, pipelined; it is not a transaction, so after an error some events may be stored, and appending them again changes nothing
  2. A read is `ZRANGE h:<user> -inf (ts BYSCORE`; for the last n events, `ZRANGE h:<user> (ts -inf BYSCORE REV LIMIT 0 n`, reversed. Members with the same score come back in byte order, which for a fixed-width hex ID is the order by ID as a number: the order of `history.Memory`
  3. Event times are 1 to 2^53 ms (`history.MaxTS`): a score is a float64, exact up to there. `/v1/events` answers 400 beyond it and the Valkey store refuses the batch; a request time beyond it reads up to `+inf`
  4. Retention is that of `history.Memory` (D023, point 2): every event is kept, with no cap per user and no expiry
  5. The compose Valkey runs with `maxmemory 1gb` and `maxmemory-policy volatile-lru`: only keys with a TTL are evicted, which the result cache's will be once it moves to Valkey (TASKS, M3), and the histories have none. Once they fill the memory, `ZADD` answers `OOM command not allowed when used memory > 'maxmemory'` while reads go on (checked by hand against Valkey 9.1 with `maxmemory 1mb`; a `SET` with a TTL failed the same way, there being nothing to evict). `/v1/events` then answers 503 and logs the error, and the client may send the events again; a test covers this with a store that refuses writes. Once events go through Kafka, the broker still takes them, and the ingest consumer leaves the offsets of events it could not apply uncommitted (D035)
  6. The gateway uses Valkey with `-valkey-addr` and its in-process store without. The client connects when it is created, so a gateway given an address that does not answer fails to start. A wrong address shows at once; the price is that a gateway cannot start, or restart, while Valkey is down, although a running one degrades (SPEC §5)
  7. One contract test suite runs against both stores, the Valkey part on the compose server under a key prefix of its own: property 1 against a naive scan (300 random cases in memory, 40 on Valkey), broken by a closed upper bound; property 8 at the store, where a random set of events delivered once must read the same, for every user, time and n, as the set delivered with repeats, shuffled and in random batches, broken by storing each delivery under its sequence number in place of the event ID, and again by ordering the events at one time by arrival; events at one time under IDs whose text order differs from their numeric order; the time bound; one large batch
  8. The stores differ in one case that needs two events with the same ID and different items, a 64-bit collision of `EventID`: the in-process store keeps the first, Valkey keeps both
- Rationale: An event is one member, so applying it twice is one `ZADD` that changes nothing, and a late event lands at its own time. The ID comes first in the member and has a fixed width so that the server's tie order equals the in-process one, which the cache key (D030) and the ranker features (SPEC §8) depend on; the item follows so that a read needs no second lookup. Measured on Valkey 9.1 with 28-byte user IDs and 10-byte item IDs: 87 bytes per event for users with 1,000 events (skiplist encoding), 41 to 58 for users with 5 to 100 (listpack, up to 128 members), so 1 GB holds some 12 million events of long histories. `volatile-lru` keeps an eviction from ever removing a history: a user whose history vanished would be shown items they have seen, with nothing in the response to tell. A write that fails is visible instead
- Limits: the histories grow until the memory is full, and then no event is stored until memory is added or histories are deleted by hand. The image's defaults persist with snapshots only (`save 3600 1 300 100 60 10000`, no append-only file), so events since the last snapshot are lost if the server stops uncleanly, and only replaying the topic brings them back
- Alternatives: the raw 8 bytes of the ID in the member (8 bytes less per event, unreadable in `valkey-cli`); the item first (ties would order by item, unlike the in-process store); trimming to the last N events or a TTL per user (the seen filter loses items, D023); `allkeys-lru` (evicts whole histories silently); a second Valkey for the cache with its own policy (another server to run for a cache that already gives way first); a hash tag in the key (for multi-key commands in a cluster; there are none)

## D034 Event path through Kafka and start order
- Date: 2026-11-10
- Decision:
  1. `/v1/events` hands its events to an `events.Producer`. With `-kafka-brokers` that is `events.Kafka`: one record per event to the topic `events`, keyed by the user, the value the event as JSON with the fields a client sends (`user_id`, `item_id`, `ts`, `kind`). The event's ID is not in the record: the consumer derives it from the same four fields (`events.Decode`, `Event.History`)
  2. The producer keeps franz-go's defaults: idempotent, acknowledged by every in-sync replica, the partition chosen by a hash of the key. A user's records are therefore in one partition, in the order produced. The linger is 0, since each request waits for its records
  3. 202 means the brokers acknowledged every record. It does not mean a history holds the event: the ingest consumer applies it later, and a request that follows at once may not see it
  4. 503 means the producer failed or did not finish within `-events-timeout` (2 s by default, at least 1 s with Kafka, the client's minimum). The handler stops waiting at the timeout. Until the client has loaded the topic's metadata, it fails a record after the same time (point 9: a closed port, a silent server, a missing topic). After that it does not: a record already sent stays with the idempotent producer until its outcome is known, and during a broker outage a record not yet sent stays in the client's buffer (at most 50,000 records), since the client checks the timeout only when it writes a request or reads a response. So after a 503 some or all of the request's events may be in the topic, or reach it once the broker is back; the client sends them again, and the event ID makes that safe. A full buffer fails a record at once
  5. Records are produced under a background context, not the request's: when the context of a batch's first record ends, the client fails every record buffered for that partition, which would turn one client's disconnect into 503s for others
  6. The gateway does not create the topic, and the compose broker does not create topics on demand. The ingest consumer creates it (D035), so the start order is Kafka and Valkey, then ingest, then the gateways. A gateway does not connect at its start, so it also starts before them; until the topic exists `/v1/events` answers 503 and `/v1/recommend` is not affected. It recovers by itself: in a one-off run a record produced while the topic was being created was acknowledged about a second after it existed
  7. Without `-kafka-brokers` the producer is `events.Direct`: the gateway writes the history store in the request, 202 means stored, and the next request sees the event. Tests, the quick start and runs that need a response to depend on the events just sent use it. The two modes differ in what 202 promises (stored, or acknowledged by the broker), in whether the next request sees the event (yes, or after ingest), and in what a 503 leaves behind (a part of the batch stored, or a part of it in the topic)
  8. At shutdown the producer is closed after the HTTP servers, so a request within the drain is still produced
  9. Tests against the compose Kafka, each on a topic of its own: 600 to 607 events of 20 users in random batches land with every user in one partition and in order, over at least two partitions; an event sent twice is two records and one event in a history both are applied to; with a closed port, a server that accepts and never answers, and a missing topic, a produce fails by the client's timeout and returns at the end of its context; through HTTP, 503 without the topic, 202 after it is created, the records keyed by user, the gateway's own history unchanged, and 503 after the producer is closed
- Rationale: The topic is the one way into the histories, so gateways hold no write path to Valkey, and a slow or stopped consumer delays events without losing them (D019). Waiting for the acknowledgment makes 202 mean the event will not be lost by a gateway restart. Carrying the client's fields keeps one place that derives the ID, and keeps `kind` for a later consumer. One owner of the topic, the consumer, fixes the partition count in one place; a gateway that created it would need the same setting on every instance
- Measured (franz-go v1.22.3, Kafka 4.4.0, one-off runs): to a missing topic the first record failed after 1.0 s, the client giving up after four metadata lookups, and later ones at the record timeout; to a closed port and to a silent server, at the record timeout
- Limits: a 503 during a broker outage does not mean the events are dropped: they stay buffered in the gateway, up to 50,000 records, and are produced when the broker returns, so a client that retries sends them a second time and relies on the event ID. A gateway that stops first loses the buffered ones. `kgo.AllowIdempotentProduceCancellation` would fail such records at the timeout, at the price of duplicates the broker cannot detect, and is not set
- Alternatives: wait until ingest has applied the event (read-your-writes, but every write would wait on the consumer); write Valkey and Kafka both from the gateway (two paths that can disagree); `ProduceSync` under the request's context (point 5, and it cannot return while a sent record's outcome is unknown); the event ID in the record (drops `kind`, and two places would compute it); topic creation on demand by the broker (one partition by default, and a mistyped name becomes a topic)

## D035 Ingest consumer: apply, then commit
- Date: 2026-11-10
- Decision:
  1. `cmd/ingest` runs one member of the consumer group `ingest` (`-group`) on the topic `events` and writes the Valkey history store (`-valkey-addr`). At its start it creates the topic with 6 partitions and the broker's default replication factor; a topic that exists is used as it is. A group without committed offsets reads the topic from its beginning. Several instances share the partitions. `/metrics` and `/livez` are served on `-addr` (:8082). `-session-timeout` (45 s, the client's default) is how long the group waits for a member that stopped without leaving before it gives its partitions to the others
  2. The loop polls, applies the batch to the store partition by partition, commits the polled offsets synchronously and only then allows a rebalance. Auto-commit is off. A consumer that stops between the apply and the commit gets the batch again, and applying an event twice changes nothing (D033), so delivery is at least once and the histories are those of every event applied once
  3. Rebalances are blocked from a poll to the commit of its batch (`BlockRebalanceOnPoll`), so a commit never covers a partition that has moved to another member. When partitions are revoked, and when the consumer leaves, it commits the polled offsets once more unless the last batch is not applied; a commit that failed in the loop is retried there and by the next batch's commit
  4. A partition's records that the store refuses, with Valkey down or full (`OOM`, D033 point 5), are tried again after 100 ms, doubling up to 5 s, until they are applied or the consumer is stopped. The batch's offsets stay uncommitted, also at shutdown. `recserve_ingest_apply_failures_total` counts the refused attempts
  5. A record that is not a valid event (`events.Decode`: the JSON and the checks of `/v1/events`) is skipped and its offset is committed with the batch: it would fail the same way every time and stop its partition for good. `recserve_ingest_records_total{result}` counts records as `applied` or `poison`; `applied` counts deliveries, so a redelivered event counts again. The log names a poison record's topic, partition, offset and length, not its content
  6. Property 9 runs a series of consumers of one group while events keep arriving (8 users, 30 items, 50 times, a quarter of the events repeats). Each consumer is stopped at one of four points of the loop, chosen by a seeded generator: batch fetched, first partition applied, batch applied but not committed, committed. Stopped means that the loop returns at once and the client leaves the group without committing, through a hook that costs a nil check in production. A last consumer catches up, and every history must equal the one of each event applied once. The broken variant commits a batch before applying it and loses the batch of a consumer stopped in between
  7. That test runs in process on kfake (4 seeds of 40 consumers, an in-process store) and against the compose Kafka and Valkey (30 consumers); the run on the real broker is the reference. kfake (`franz-go/pkg/kfake`, a pseudo-version, test only) is used for this one test, so that the property is checked where Docker is not; D038 point 3 holds for everything else. In a one-off count over the 160 kfake consumers, each point stopped 32 to 45 of them, and 1,294 distinct events were applied about 3,300 times
  8. Against the compose services: property 8 through the topic, where 400 events with repeats, each sent up to two more times and shuffled, are produced by `events.Kafka` in random batches and the Valkey histories must equal those of each event applied once (its broken variant is the store's, D033 point 7); a second member joins and the first leaves while events arrive; poison records between valid ones, which the next member must not get again; a store that refuses appends, under a consumer that shuts down holding the batch and under the next one until the store recovers; topic creation, twice. A test knows that the group is through the topic by producing a last event to every partition and reading it from the store
- Rationale: Committing after the apply turns a crash into a replay, and the store makes a replay harmless (D019), so no transaction has to span Kafka and Valkey. Blocking rebalances while a batch is in hand removes the case of a member committing offsets of a partition it no longer owns. Applying partition by partition keeps one append per partition's records. Skipping a poison record trades one event, which no retry would recover, for the partition's progress
- Limits: while a batch is retried the member blocks rebalances; if one is due, the group removes the member after the rebalance timeout (60 s, the client's default) and another member applies the same batch, so events may be applied twice and none is lost. A poison record never reaches a history, and only the counter and the log show it. A topic that exists with another partition count is not changed. A fetch error the client does not retry, as for a topic deleted and created again while the consumer runs, is logged once a second and ends only with a restart: on the compose Kafka the consumer never read the new topic. If the brokers or Valkey cannot be reached at the start, the process exits and whatever runs it must start it again. That the commit at leaving works was checked once with the loop's own commit turned off: the next member received nothing. A member killed without leaving holds its partitions until its session times out, and a member that starts meanwhile waits as long
- Alternatives: auto-commit (commits polled offsets on a timer, applied or not); commit before apply (the broken variant); a Kafka transaction (cannot include Valkey, D019); a dead-letter topic for poison records (a second topic and its consumer, for records that only a foreign producer or a bug creates); stopping at a poison record (the partition stops with it); allowing rebalances between retries (the held batch would have to be dropped and its offsets rewound)

## D036 Result cache on Valkey
- Date: 2026-11-10
- Decision:
  1. With `-valkey-addr` the result cache is on the Valkey server that holds the histories (`cache.Valkey`), shared by every gateway; without it the cache stays in the process (D030 point 4). `-cache-size 0` turns either off. On Valkey the size means nothing else: the server's `maxmemory` bounds the cache, and `volatile-lru` evicts the entries least recently used and never a history (D033 point 5)
  2. An entry is the string `c:<key>`, the key of D030 point 1 as 64 hex digits, holding the response as the JSON that `/v1/recommend` answers (items, model version, degraded, coverage), set with `SET PX` at `-cache-ttl` times a uniform factor in [0.9, 1.1]. Go writes a float64 as the shortest decimal that reads back as the same value, so a hit returns every score bit for bit
  3. The pipeline uses either cache through one interface, `recommend.Cache`: a read and a write, each with a context and an error, each run within `-budget-history` (the read within what the history read left of it, since D037 point 4). An error of either, a timeout included, is not a degradation: the request is answered in full as a miss, `recserve_cache_lookups_total{result="error"}` counts it once, and an error other than a timeout is logged. A request that fails after its lookup is counted as before, as a miss or an error. A request that ends while the cache is written is no cache error. If the request's own context ends during the read, the request fails as in any stage (D029 point 2)
  4. The cache has a client of its own, made as the history store's is (D038 point 2; `valkeyclient` since D037 point 7). Like the store's, it connects at the start, so a gateway does not start while Valkey is down (D033 point 6)
  5. Cache entries give way to histories: when memory runs out the server evicts entries to take a history write. Once the histories alone fill it there is nothing left to evict, and a cache write fails with `OOM` as a history write does (D033 point 5); a request that misses is then counted as an error, and logs a warning
  6. The key still holds the history, so a hit reads the history first (D030). A per-user history version, bumped by ingest with every append, would save that read and is not built: see the figures below
  7. Gateways on one Valkey may differ in `-shards`, `-shard-mode` and `-hnsw-ef`, which D030 point 2 could call fixed for the cache's life. The key now holds the shard settings, so such gateways do not share entries
  8. Tests against the compose Valkey: property 5 and its broken variant with the cache on Valkey; two pipelines with a client each, as two gateways, where the second answers from the cache what the first computed, equal to its own computation item by item and score by score and equal as JSON; in `internal/cache`, 1,007 float64 values, the largest and smallest included, read back bit for bit by a second client, times to live of 200 entries spread over 90 to 110 s for 100 s, expiry, and a malformed entry as an error. With a cache that fails to read, or only to write, the response equals the one without a cache, is not degraded and is counted as an error. Tests on the shared server salt their keys
  9. Requests that miss the cache on one key at the same time compute the response once per gateway (`golang.org/x/sync/singleflight` v0.25.0, keyed by the cache key). The first, the leader, computes and writes the cache; the others wait, each as long as its own context allows, and return the leader's response, degraded or not, as a miss. A leader fails only when its own context ends: the requests that waited then start over, and the first of them leads; one that starts over after that computation has ended computes again, without a second look at the cache. A request joins after its history was read and the cache missed or failed, so one without its stored history computes alone. The computation runs in a goroutine of its own, and the leader waits for it, also once its context has ended (D029 point 4)
  10. Property 11: 16 identical requests, each computation held at the encoder until all 16 have joined, compute once and get the same items; the broken variant bypasses the group and computes 16 times. With the leader's context cancelled, the 7 other requests are answered in full
- Measured (one-off, code not committed; a 4-CPU machine, compose Valkey over loopback, a synthetic bundle of 2,000 items, 2,000 hits per case): a hit took p50 0.15 to 0.34 ms and p99 0.5 to 1.7 ms for histories of 10 to 500 events at k of 50 and 100, the history read included; the history read alone took p50 0.06 to 0.19 ms, about half of it. In process a hit took p50 2 µs (D030). An entry at k = 100 with 10-byte item IDs is 4,757 bytes of JSON and takes 5,216 bytes on the server (`MEMORY USAGE`), against about 3.1 KB in process
- Rationale: A shared cache keeps the gateways interchangeable: a response one of them computed serves all, and a restart loses nothing. An error is a miss because the cache only saves work: its failure must not change a response, and `degraded` lists what did change it. JSON is the form the response already has, readable with `valkey-cli`, and its floats are exact. At 0.2 to 0.3 ms a hit is well inside the 3 ms of its stage (SPEC §5), so the read a history version would save does not pay for a second write path in ingest
- Limits: a miss writes the cache before it answers, one more round trip on the request path, since nothing a request starts outlives it (D029 point 4). With a slow Valkey whose history read still succeeds, a request could spend the history budget three times: history, cache read, cache write (twice since D037 point 4). Gateways of two builds share the entries during a rollout, so a change to the response's fields, or to how a build ranks, must come with a new key prefix; so must a bundle rebuilt under a version it already had. A request cancelled during the cache read fails without being counted. The budget on the cache calls has no test. The cache's size and evictions show only in the server's own statistics. A request that shares a leader's response is counted as a miss, and no metric tells it from the leader; the ranker's dropped count and the logged errors stay with the leader. A panic in a shared computation ends the process: it runs outside the HTTP handler's goroutine, where `net/http` would have recovered it
- Alternatives: a second Valkey for the cache (D033); a binary encoding (smaller entries, unreadable, and one more format to keep compatible); writing the cache after the response is sent (work outliving its request, D029); an in-process cache in front of Valkey (hits in microseconds again, at the price of two caches to keep in step); a per-user history version in the key (point 6)

## D037 Circuit breaker on the gateway's Valkey calls
- Date: 2026-11-10
- Decision:
  1. With `-valkey-addr` the gateway's history reads and its cache reads and writes go through one circuit breaker (`internal/breaker`, on `github.com/sony/gobreaker/v2` v2.4.0). It opens after 5 failed calls in a row, of any of the three. While it is open a call fails at once and does not reach Valkey. After 1 s one call at a time is let through: the first that succeeds closes the breaker, one that fails opens it for another second. Both values are constants of the gateway
  2. An open breaker needs no path of its own in a request: a refused history read is a failed one, so the response comes from the request's `recent` items, reports `history_unavailable` and neither reads nor writes the cache (SPEC §5, D029). The refusal is not logged with each request; the breaker logs its changes of state at warning level
  3. A failure is any error of a call, the end of its budget included, except one that wraps `context.Canceled`: a client that went away says nothing about Valkey. Appends (`/v1/events` without Kafka, `-preload`) do not go through the breaker
  4. The history read and the cache read now share one `-budget-history`; the cache write gets it once more, and a request whose cache read failed does not write. A request so waits for Valkey at most twice the budget, the second time only after Valkey answered in time; before, three times (D036)
  5. A gateway still does not start while Valkey is down (D033 point 6): a client must connect once to be created (point 7). Starting with the breaker open would show a wrong address only as degraded responses
  6. Property 10 runs a pipeline on the compose Valkey behind a TCP proxy of the test (`infratest.Proxy`), which refuses connections or accepts them and never answers. The user's stored history equals the `recent` items of its requests, so a response computed from them has the cache key of a healthy one. Valkey first returns in the middle of a request, after its history read failed and before its response could be stored; then, through an outage of 20 requests, each must be answered within 1 s with the items of a pipeline whose history is the recent list, and report `history_unavailable`; once Valkey is back, a request with that history must never hit the cache and is soon answered in full. The broken variant stores degraded responses and is caught by a hit that reports `history_unavailable`, in both modes. In `internal/breaker`, with a store and a cache that count calls: three failures in a row across both open the breaker, no call reaches them while it is open, a failed trial opens it again, a success closes it, and cancelled calls count as neither. The integration tests stop Valkey under the gateway binary (TASKS, M3)
  7. Connections to Valkey are opened and replaced in the background, never within a request (`internal/valkeyclient`, which the history store, the cache and ingest use). valkey-go v1.0.79 cannot do this by an option. A client connects one of its connections when it is created and every other one, and every replacement, inside the call that first needs it, handshake included, under that call's context (`mux.go` `_pipe`, `pipe.go` `_newPipe`); `Dialer.Timeout` only caps that context; calls that arrive meanwhile wait for the same attempt without watching their own context; nothing warms the connections or reconnects them, and a command cannot be aimed at one of them. So a `valkeyclient.Client` holds four valkey-go clients, the library's own number of connections for one server on four or more CPUs, each limited to one connection (`PipelineMultiplex: -1`) and to one dial (`DialCtxFn` refuses a second), made when the client is created, under no request's context; the TCP connection and the handshake may each take 1 s. The clients queue every call for the connection's reader and writer (`AlwaysPipelining`): without it valkey-go runs a call that overlaps no other directly on the connection and closes the connection when the call's deadline passes, so every read past its budget would cost a connection, and a connection the server closed would be noticed only by the next call. One goroutine creates them and replaces each whose network connection was closed, which the connection handed out by `DialCtxFn` reports; after a failed attempt it tries again every 100 ms. A call takes one of the connected clients at random. If its connection is lost during the call and its context has not ended, the call runs again on another, so a call must be safe to repeat, and commands are built anew for each run; the store's and the cache's are (`ZADD NX`, `ZRANGE`, `GET`, `SET`). With no connection, a call waits for one as long as its context allows and then fails with `ErrConnecting`, which the breaker counts as neither a success nor a failure: the request degrades as for any failed read, and says nothing about the server. Once an attempt that began with no connection has failed, or 1 s after the last connection went, calls fail at once, each a failure to the breaker, until an attempt succeeds. An attempt that began while a connection was still up does not count: it may have failed with that connection, as when a proxy drops them all. The error of a failed attempt does not wrap the attempt's own, so a handshake that timed out is not taken for the timeout of the request that is told of it. The store and the cache take the client they run on; the gateway gives each its own (D036 point 4)
  8. The test of point 7 runs a request's calls (history read and cache read in one budget of 350 ms, cache write in another) through a breaker with the gateway's settings, on the compose Valkey behind the proxy, which holds every new connection back for 550 ms. At the start, and again after the proxy closed every connection, the breaker must not change state, a request must succeed within 10 s, and the 49 after it must all succeed. The broken variant is valkey-go's own client with the options of D038 point 2, as before this point: its calls on the connections not yet open, three of four on four or more CPUs and all of them after the drop, end at their deadline, and the breaker opens. Two more tests: with connections refused, calls fail within 50 ms with an error that is not `ErrConnecting`, and succeed again once the proxy passes them; a server that accepts a connection and never answers fails `New`
- Measured (one-off, a 4-CPU machine, history budget 100 ms): against the silent server the four requests before the breaker opened took 100.6 to 101.3 ms each, so a call ends at its context's deadline (D038, known issues), and the 16 after it 40 to 300 µs; with connections refused all 20 took 30 to 390 µs
- Measured for point 7 (one-off, the same kind of machine, compose Valkey over loopback, code not committed). One connection against four, 20,000 `ZRANGE` reads per worker, two runs each: of a 20-member set, one connection was level or ahead (4 workers p99 426 to 447 µs against 503 to 547 µs); of a 500-member set, behind (4 workers p50 434 to 468 µs against 353 to 362 µs, p99 1.78 to 2.04 ms against 1.45 to 1.47 ms; 16 workers p99 4.9 to 5.9 ms against 4.3 to 5.6 ms), so four connections stay. The same reads on one connection with and without `AlwaysPipelining`: level with 4 workers (500 members, p99 2.3 to 2.4 ms both ways), and with one worker p50 253 to 270 µs against 217 to 225 µs and p99 1.01 to 1.03 ms against 0.90 ms on 500 members, level on 20. The stage check of D039 (`TestRealDataValkey`, Valkey with the cache on, without the noise baselines of its protocol), three runs before the change and three after, taken in turn: stage p99 in the round that computes 3.0 to 5.7 ms before and 2.9 to 4.9 ms after, in the round that hits 1.0 to 2.5 ms before and 0.8 to 2.1 ms after; p50 0.41 to 0.58 ms before and 0.38 to 0.48 ms after. The runs differ among themselves by more than the two sides do. In the test of point 8 the first request succeeded about 0.7 s after the connections were closed
- Rationale: A Valkey that does not answer costs every request its history budget, 3 ms of a 50 ms target, for a read that will fail; the breaker turns that into no wait and keeps the gateway off a server that is restarting. One breaker for the three calls, since they go to one server: the cache failing is a sign the history read will. Counting failures in a row is the library's own default and needs no window to tune
- Limits: each gateway has its own breaker and learns of an outage by itself. Five failures in a row open it for every user, also when they come from one user whose history is too long to read within the budget. Failures that alternate with successes never open it. A request past its caller's deadline counts as a failure. While a trial call runs, other requests are refused. Before point 7 the client opened a connection, handshake included, within the budget of the request that first used it, so where setup takes longer than `-budget-history` (TLS, a distant server, busy CPUs) the breaker opened with Valkey healthy and stayed open: on idle loopback a first use took 0.7 to 3.1 ms, and with 6 ms added to connection setup alone 8 of 1,500 reads succeeded after the start and none after the connections had dropped once (one-off, by the M3 review). Since point 7: with every connection lost and the server accepting new ones without answering the handshake, requests wait out their history budget for up to 1 s without a failure being counted; only then do calls fail at once and the breaker open. A server that goes silent on open connections is different: calls end at their deadline, each a failure, and the connections stay until valkey-go's ping, sent after an idle second, has waited its 10 s for an answer (from the source; not measured). A call in flight when its connection is lost may get the connection's error before the client knows of the loss, and then fails instead of running again. `Close` waits for an attempt that is running, up to 2 s. The four are replaced one after another, so after all were lost the client is back to four only after four setups; calls run on those already open. A failed attempt to connect is not logged and has no metric; with the last connection gone it shows as the breaker opening. A valkey-go client here refuses a second dial, so a command the library would send on a connection of its own (a blocking command, a pipeline of 2,000 commands or more) fails; the gateway and ingest send none. The timeout of an attempt and the wait between attempts are constants. A cache call that the breaker refuses just as it opens is still logged and counted as a cache error, once per such request. The state shows only in the log, not in a metric
- Alternatives: a breaker per kind of call (three states for one server); a failure rate over a window (gobreaker has it; two more settings); a hand-written breaker (the library already has the half-open state and the exclusion of chosen errors); letting the gateway start with the breaker open (point 5); the breaker inside the Valkey clients (`/v1/events` and ingest would share the gateway's policy); for point 7: `DialCtxFn` dialing under a context of its own (covers the TCP connection but not the handshake, and the call would wait past its budget); pings that warm valkey-go's own four connections (a keyed command takes one at random, and a call that joins a slow attempt waits it out); one connection per client (simplest, slower on long histories, measured above); counting a wait for a connection as a failure (the breaker would open on slow setup again)

## D038 Valkey and Kafka clients and test infrastructure
- Date: 2026-11-10
- Decision:
  1. The Valkey client is `github.com/valkey-io/valkey-go` v1.0.79, in place of go-redis (D020). `internal/history/valkey.go` and `internal/cache/valkey.go` import it, and reach the server through `internal/valkeyclient` (D037 point 7)
  2. Options: `ForceSingleClient` (one server, no cluster probe), `DisableCache` (no client-side caching, so no `CLIENT TRACKING`), `DisableRetry`; since D037 point 7 also one connection per valkey-go client and a dial timeout of 1 s. By default the client retries a read-only command after a network error until the context ends, which without a deadline is forever; a failed read is left to the caller, who degrades (D029)
  3. Tests that need Valkey or Kafka run against the compose services (`make infra-up`). `internal/infratest` reads `RECSERVE_VALKEY_ADDR` and `RECSERVE_KAFKA_BROKERS`, and creates and reads test topics; without the variable a test is skipped, and with `RECSERVE_REQUIRE_INFRA=1`, as in CI's integration job, it fails. No in-process fake (miniredis) and no testcontainers-go
  4. The Kafka client is `github.com/twmb/franz-go` v1.22.3. Consumer groups use the classic rebalance protocol, not KIP-848's. Topics are created and deleted with the protocol messages of `franz-go/pkg/kmsg`, the module franz-go itself depends on, at the version it requires (v1.15.1); `pkg/kadm` is not added
  5. `internal/e2e` builds the gateway and ingest binaries and runs them against the compose services with the 12-item test bundle: an event sent to `/v1/events` leaves the user's recommendations once ingest has applied it, which the test polls for; ingest is killed with SIGKILL five times at random moments while 2,400 events arrive, a quarter of them repeats, and restarted in its group, after which every history in Valkey equals the one of each event applied once; with the Valkey container paused, 40 requests each get 200 within 1 s from their `recent` items with `history_unavailable`, and the stored history is used again after it; with the Kafka container stopped, `/v1/events` answers 503 and `/v1/recommend` is not degraded. The last two take the services away from every other test, so the package runs only with `RECSERVE_E2E=1`, by `make e2e` and as its own CI step after the other tests
- Rationale: go-redis v9.23.0 lists Redis CE 8.0 to 8.10 as supported and not Valkey; its handshake sends `HELLO 3`, `CLIENT SETINFO` and `CLIENT MAINT_NOTIFICATIONS` and works with Valkey by tolerating errors. valkey-go is the Valkey project's client; with the options above its handshake is `HELLO 3` and two `CLIENT SETINFO` (v1.0.79, `pipe.go`), which Valkey 9.1 answers. A fake would have to reproduce the tie order of a sorted set and the behavior at full memory, the two things the store's tests are about
- Known issues: rueidis #858, reported against the client valkey-go derives from: a command does not honor its context's deadline while the connection's ring buffer is full; against a server that accepts connections and never answers, a call of this client returned at its deadline (D037, measured), so it did not show here. A built command cannot be built or sent twice (the builder panics)
- Alternatives: go-redis (above); testcontainers-go (a container per test run and a large dependency, for services compose already starts)

## D039 Checks of the Valkey path before M3 closes
- Date: 2026-11-10
- Decision:
  1. Two measurements, their protocol and pass criteria committed to docs/BENCHMARKS.md (Valkey path) before either ran: the time a request spends reading its history and looking up the cache, in the process and on Valkey, on 2,000 real requests from four workers; and three load runs at 200 requests/s against a gateway on Valkey and Kafka
  2. The stage passes at a p99 of 3 ms, its budget in SPEC §5. If it fails, the per-user history version of D036 point 6 is built only if reading a small key is at least 30% faster at p99 than reading a history under the same conditions: the version saves the history read on a hit and puts a small read in its place, so it helps only as far as the two differ
  3. The load runs pass if all three are valid and have p99 ≤ 50 ms. They are an interim figure for M3 at one rate: the sweep, the cache-off scenario, the writes and the headline stay with M6
- Outcome (docs/BENCHMARKS.md, M3): the load runs pass, p99 10.9 to 12.0 ms, with 0.2 to 0.3% of the responses reporting `history_unavailable` for a read past the budget; none of their 14,000 requests hit the cache, since replaying the test split repeats no request, so here the cache only costs. The stage check fails: on Valkey with the cache on, the p99 of three runs is 2,902, 4,343 and 5,796 µs (median 4,343 µs) in the round that computes and 812, 2,353 and 1,679 µs in the round that hits. It is recorded as not met with four workers saturating the four CPUs that Valkey shares, and M6 measures the share of requests past the budget at each rate of the sweep. The history version is not built. Two small-key readings exist. The control, read while nothing computed: p99 306, 745 and 450 µs, 33 to 89% below the history read's p99 of its run. The cache lookup of the failing round, a `GET` that finds nothing, read under that round's load: p99 2,145, 3,176 and 3,878 µs, against 2,336, 2,973 and 3,971 µs for the history read, at most 8% below it and once above. Point 2 asks for the same conditions, and only the second reading has them: the control as BENCHMARKS specified it did not run under the load of the round it is compared with. Judged by the second, the condition does not hold. Besides, the version would save the read only on a hit, where the stage passes
- Found in M6: compose's Kafka health check started a JVM every 2 s, which kept about two thirds of a CPU busy while the broker idled (docs/BENCHMARKS.md, Environment record). The stage check and the load runs above ran with that load, as did M5's runs in compose; none was rerun. The figures of D047 and D050 come from kind, which runs no Kafka, and do not include it
- Rationale: M3 moved the first stage of every request onto the network, and its budget was set before that. Measuring the stage on its own tells whether Valkey fits the budget before the load tests of M6 depend on it, and the control separates the cost of a round trip from the cost of a long history
- Alternatives: wait for the M6 sweep (a stage over budget would show there only as degraded responses); build the history version first (D036 point 6: a second write path in ingest, for a read that may cost little)
- Outcome in M6 (docs/BENCHMARKS.md, M6): the share of requests whose history read or cache call ran past the budget grows with the rate. With the cache off: at most 0.07% of a run to 550 requests/s, 1.93% in one run of 800/s, then 12 to 19% at 1,200/s and 55 to 69% at 1,600/s, in whole seconds that match the circuit breaker (D037). With the cache on, one run of 400/s had 1.74%, so by the rule of BENCHMARKS the headline rate, 550/s, ran with 5 ms: 0.02, 0.00 and 0.00% in three runs. SPEC §5's budget for the stage becomes 5 ms, and "other overhead" 7 ms, keeping 50 ms end to end. The per-user history version stays unbuilt, and D039 is closed

## D040 annshard API: gRPC, and the request names the index
- Date: 2026-11-10
- Decision:
  1. `proto/recserve/annshard/v1/annshard.proto` defines the service `AnnShard` with two unary methods, `Search` and `Prepare`, in proto3 with the plain generated structs. The server also registers the standard `grpc.health.v1` service
  2. Every request carries an `Index`: the bundle version, the shard and the number of shards, the mode and the HNSW build parameters. `Prepare` loads the version's directory under the replica's `-bundles` root, verifies `items.npy` against the manifest and builds that one shard; it is idempotent. `Search` answers only from the index its request names and fails with `FAILED_PRECONDITION` if the replica does not hold it. A replica so has no shard settings of its own: `annshard` takes `-addr` and `-bundles`, and which shard it serves, of how many and in which mode is the gateway's to say. The gateway lists the replicas in a flag, `-shard-addrs`, shards separated by `;` and a shard's replicas by `,`; D004 planned a config file
  3. A search carries the query as float32, k, the IDs to leave out and the HNSW search list size, and returns int32 IDs with float64 scores, best first, ties to the lower ID. D002 planned float32 scores
  4. The Go code is generated by the buf CLI (v1.75.0) with `protoc-gen-go` v1.36.12 and `protoc-gen-go-grpc` v1.6.2, which go.mod pins as tools and `buf.gen.yaml` runs through `go tool`; no protoc is installed. `make proto` lints the proto files (buf's `STANDARD` rules without `SERVICE_SUFFIX`) and regenerates; the generated files are committed, and a CI job fails if generating changes the tree
  5. In the gateway the pipeline searches through `recommend.Shards`: the shard settings and one search of one shard, with the set of seen items. `shard.Set` implements it in the process and `annshard.Shards`, one bundle version on the replicas, over gRPC, so the retrieval code of D028 and D029 (deadlines, merge, coverage, reasons) exists once. The client sends a shard only the seen IDs that belong to it, and the search list size with every search
  6. A shard's context is the one of D029 point 1; gRPC carries its deadline to the replica, whose exact search checks it every 1,024 rows. The client turns `DEADLINE_EXCEEDED` and `CANCELLED` back into errors that wrap the context's, so a shard past its budget is a timeout and anything else a failure, as in the process: D028's merge and D029 points 2, 3 and 5 hold unchanged. D029 point 4 holds in the gateway: every call a request made has returned before the request does. On the replica a search whose caller has gone runs on to its next check of the context
  7. A gateway given `-shard-addrs` loads and verifies a bundle as before, then has the replicas prepare its version, at start and in a swap, within `-prepare-timeout` (2 minutes); `-shards` is then the number of address groups. The cache key holds the shard settings and not where the shards run, so gateways with shards in the process and on replicas share entries: their responses are equal
  8. Tests: property 6 runs through one check, `shardtest.CheckProperty6`, on the in-process shards and on replicas, and the pipeline's check likewise, each with its broken variant (ceil(k/n) items per shard). In HNSW mode a search through the client equals the in-process one hit by hit, so the replicas build the graph the gateway would. The shard cases of D029 run against two shards behind a TCP proxy that refuses connections (an error) or accepts them and never answers (a timeout at the shard budget), and every response must be the one the in-process shards give with those shards skipped. A replica refuses a search for an index it did not prepare, also one that differs from a held index in version, shard, split or mode
- Measured (one-off, not under the benchmark protocol; the 4-CPU M4 machine, loopback, no race detector; `TestRealDataShardsOverGRPC`, three runs): on the Video_Games bundle on two shards of two replicas each, 2,696 shard searches of the 2,000 real requests of D028 (k = 200), one at a time, each run in the process and then through a replica. Exact: p50 0.92 to 1.01 ms and p99 1.88 to 2.10 ms in the process, p50 1.58 to 1.90 ms and p99 3.14 to 3.55 ms through a replica. HNSW (ef 400): p50 0.29 to 0.32 ms and p99 0.56 to 0.77 ms in the process, p50 0.64 to 0.78 ms and p99 1.27 to 1.71 ms through a replica. The call so adds 0.3 to 0.9 ms at p50 and about 1 to 1.5 ms at p99, and the hedge delay's default of 5 ms (D041) lies above the p99 of an idle replica; under load it is M6's to measure. Every search and every response equalled the in-process one, in both modes. Under the race detector the test takes about 4 minutes, which brings `make test-real` to about 21
- Rationale: With the index in the request, a replica cannot answer from another version or another split than the request means: it has the named index or it says so, and a response never mixes versions (property 4) whatever the replicas hold while a swap rolls out. The layout lives in one place, the gateway, so a replica's settings cannot disagree with it; a replica that held its own shard number would answer a misrouted request from the wrong items with nothing to tell. Scores are float64 because the merge compares scores across shards and must equal the in-process merge item by item (property 6): `vec.Dot` sums in float64, and two scores that differ there may round to the same float32. Generated files in the tree keep `go build` free of a generator, and tools pinned in go.mod make the output depend on the repository alone
- Limits: no TLS and no authentication between the gateway and the replicas. A deployment must make the replicas' port reachable from the gateways only; the kind manifests do it with a NetworkPolicy (D047). A replica trusts the version in a request as a directory name under its root, after refusing anything but a plain file name. It verifies `items.npy` against the manifest in its own directory, not against the gateway's, and the version against the checksums (D046), so a replica given other vectors under a version's name fails to prepare it. The client still checks that every returned ID is an item of the gateway's bundle, which has no vector for any other: an answer that holds another is a failure of that replica, which names it and the version; the shard's other replicas are asked (D041 point 3), and with none left the shard is left out and the error logged. Equal graphs on every replica need a reproducible build, so a replica builds an HNSW index with one goroutine. An HNSW search still checks its context only before it starts (D028)
- Alternatives: shard settings as `annshard` flags (above); float32 scores (half the bytes of a score, a merge that can differ from the in-process one); a streaming search (one answer per request needs none); buf's remote plugins (generation would need the registry, and the plugin versions would be pinned outside go.mod); protoc installed by hand (one more tool whose version CI and each machine must agree on); the opaque API or protobuf editions (nothing here needs lazy decoding or field presence)

## D041 Replicas: selection, failover and hedged searches
- Date: 2026-11-10
- Decision:
  1. The gateway holds one gRPC connection per replica of the static list (`-shard-addrs`); gRPC opens it, keeps it and connects again after a loss. Its defaults stay but for three: the wait between attempts to reach a replica that is down grows to at most 5 s (the default is 2 minutes), an attempt may take 5 s (20 s), and the DNS resolver resolves a replica's name again at most once a second (30 s). The last is process-wide, set by the gateway at start (`dns.SetMinResolutionInterval`): a replica restarted under its name, as a StatefulSet's Pod is, comes back on another address, and when its connection drops the name still resolves to the old one, so with 30 s between resolutions the gateway could reach the new address 30 s after the replica was ready (Measured). The resolver resolves only when a connection is lost or an attempt to connect fails, never on a timer, so a gateway sends at most one lookup per replica per second, and only while that replica cannot be reached
  2. A shard search asks one replica: of those whose connection is ready, a different one each time, in turn; if none is ready, the first as listed. A connection that gRPC let go idle after a loss is told to connect, since no search would be sent to wake it
  3. Failover: when a call fails, the search asks the next replica at once, within the same deadline, each replica at most once. A call ended by the deadline or by cancellation is not a failure and is not tried elsewhere: the shard is then a timeout as before (D040 point 6). If no replica answers and at least one failed, the search returns the failures alone, also when another replica then ran out of time, so the shard counts as failed and the error is logged (D029 points 2 and 5). Failover takes nothing from the hedge budget
  4. Hedging: when the replica asked first has not answered after `-hedge-delay` (2.5 ms since M6, from calls measured under load, below; 0 turns hedging off), the search asks one more replica, the next one whose connection is ready. The first answer wins, the other call is cancelled, and the search returns only when every call it made has returned (D029 point 4). A search sends at most one hedge
  5. Hedge budget: each shard has a token bucket. Every search adds a tenth of a token, up to 10 tokens, and a hedge takes one; without a token the search waits for its first replica. The bucket starts full, so over n searches a shard sends at most 10 + n/10 hedges, whatever the replicas do
  6. The gateway does the hedging itself. grpc-go v1.85.0 implements the retries of gRFC A6 and not its hedging: `service_config.go` parses a retry policy and no hedging policy. Its retries are not used either: they would run inside one call, where they could not share a budget with hedges
  7. Metrics: `recserve_shard_hedges_total{shard, result}` with the results `won` (the second replica answered first), `lost` and `denied` (the budget was spent), and `recserve_shard_failovers_total{shard, replica}`, counted under the replica that failed, by its address as `-shard-addrs` gives it, and only when the search goes on to the next replica. With one replica that fails every search and one that answers, the count is under the failing one's address alone; counted under the replica asked next, the test fails (checked once, by hand). `recserve_shard_search_seconds{shard}` (M6, D052) is a histogram of every call to a replica, from its send until it returns, whatever its result, with buckets every 0.25 ms up to 5 ms
  8. Keepalive: when nothing has been read from a replica for 10 s the client pings it, also with no call in flight, and closes the connection if no answer comes within 3 s. A replica that goes silent with its connection up, as a paused process or a dead network path does, so stops counting as ready 13 s after its last byte, and from then on its shard's searches go to the other replicas without a hedge. 10 s is the shortest interval grpc-go lets a client ping at (`dialoptions.go` raises a smaller one to `internal.KeepaliveMinPingTime`); 3 s is short beside it and far above a ping's round trip. The replicas' servers accept pings 5 s apart and without a call in flight (`annshard.ServerOptions`): grpc-go's default takes pings less than 5 minutes apart for abuse and closes the connection after two. The values are constants
  9. Property 12: on two shards of two replicas each, one replica of each shard refuses connections, accepts them and never answers, or answers every search with an error; each of 10 responses must equal the in-process pipeline's, with both shards answered and nothing degraded. The broken variant is a client that knows only the lost replica of each shard. Property 13: against two replicas that each take 60 ms, with a hedge delay of 10 ms, 150 searches, ten at a time, must send between 1 and 25 hedges, and every hedge must see its caller cancel it; the broken variant hedges every slow search and sends 150. The replicas' slowness comes from a server interceptor registered by the test: the first call of a search takes 60 ms and a second call of the same search waits for its cancellation, so the hedge always loses. A delay in the network could not show the cancellation, since it delays the cancellation as much as the request and the losing handler has returned by then. Two fault tests: a replica that goes away while it holds searches costs none of them, with hedging off; a shard whose two replicas do not answer is left out at the shard budget with `shards_partial` and one of two shards answered. Keepalive: a connection to a replica that goes silent behind the test's proxy must leave the ready state within 18 s, and one opened without the keepalive, the broken variant, is still ready then; 16 s after one of a shard's two replicas went silent, 40 searches, more than the hedge budget covers, are all answered correctly and none reaches the hedge delay
- Measured (one-off, loopback): the silent connection left the ready state after 13.0 s. An idle connection to a replica stayed ready through 36 s, three pings; against a server with grpc-go's default policy the same connection was closed after 30 s with `too_many_pings`. In kind (Kubernetes 1.37, one node, three gateways; a replica's StatefulSet Pod deleted and recreated under its name, two restarts each): with the 30 s default, two of the three gateways reached the new address 30 s after the deletion and one after 1 s, while the replica was ready after 1 s, made so by that one; with 1 s, all three reached it within 2 to 3 s, at about four lookups per gateway per restart
- Rationale: A hedge trades a second call for the tail of the first: it helps when one replica is slow and the other is not. When all are slow, hedging every search would double the load on replicas that are already behind, so the extra load is capped as a share of the traffic, with a small reserve for a burst. gRFC A6 throttles retries and hedges with a token bucket per server; Finagle's `BackupRequestFilter` caps backup requests at a percentage of the requests; Envoy has a retry budget relative to the active requests. A failed call is retried at once and outside the budget because a failure is known immediately and costs the failed replica nothing more, while a slow call is still running. Round robin among ready connections needs no latency statistics and keeps a replica that is down out of the way without a health check of its own: gRPC already tracks the connection
- Limits:
  1. For the 13 s between a replica going silent and the keepalive closing its connection, the replica still counts as ready and is asked first by every second search of its shard. Those searches depend on a hedge: the reserve covers 10, after that the budget lets about one search in ten have one, and the others run to the shard budget and are reported as `shards_partial`. Property 12 holds for that fault only within the budget, which is why its check sends 10 requests
  2. The keepalive is answered by the replica's HTTP/2 transport, not by its search code: a replica that answers pings while its searches hang or crawl stays ready for good, and its searches are covered only by the hedge budget, as in the window above. There is no outlier detection and no client-side health check, and the selection does not look at latency. M6 measures both cases under load (TASKS)
  3. The hedge delay is fixed, not derived from observed latency; its default comes from one series of runs under load (below). A hedge asks for the same work again and is not tied to the first call: the losing replica learns of the cancellation only when it arrives, and an HNSW search does not stop for it. One slow replica so costs its shard's searches the hedge delay each. The budget is per gateway: n gateways may together send n times the hedges
  4. `ClientConn.Connect`, used to wake an idle connection, is marked experimental in grpc-go. The replica list is static (D004)
  5. A failure that another replica makes up for is counted (`recserve_shard_failovers_total`, under that replica) and not logged; a replica that fails every search shows in that counter alone. A failure with no replica left to ask is not counted there: the search fails and the response reports the shard missing A call cut off because the client was closed, as at a shutdown that ran past `-drain`, reads as cancelled although no context ended; it is still kept as a failure
  6. Messages have grpc-go's default size limit, 4 MB to receive. A search sends the seen IDs of one shard, at most that shard's items, about 3 bytes each at this catalog's size: 40 KB for the Video_Games bundle, and above the limit only for a shard of more than a million items all of which one user has seen; the replica would then refuse the search (`RESOURCE_EXHAUSTED`) and the shard be left out for that user
- Updated in M6 (docs/BENCHMARKS.md, M6, fault runs): at 275 requests/s with the cache on, 11.75 to 12.11% of the responses in the 13 s after a replica's pause, and 11.18 to 11.51% while a replica's searches hang, report `shards_partial`, above BENCHMARKS's 1%, so outlier detection is adopted. Design: a replica whose calls end at the shard deadline a number of times in a row, with no answer, leaves the selection as a replica without a ready connection does (point 2), and after a wait one search is let through to it; an answer brings it back. The count and the wait are to be set from measurements. It is not built in M6 (TASKS, M7), so Limits 1 and 2 still hold
- Updated in M6 (docs/BENCHMARKS.md, M6, hedge delay): with hedging off at 275 requests/s and the cache off, the larger shard's p95 of a call to a replica was 2.20, 2.05 and 1.99 ms in three runs, so the default becomes 2.5 ms, the median rounded up to 0.5 ms (it was 5 ms, from one idle replica). With 2.5 ms, 1.0 to 1.3% of the searches sent a hedge, fewer than the 5% the rule aims at, since the rounding up takes the delay past most of the slowest 5% of calls
- Alternatives: gRPC's own retry policy (no hedging in grpc-go, point 6); hedging without a budget (the broken variant of property 13: every slow search sent twice); a hedge delay that follows the observed p95, as "The Tail at Scale" is usually cited for (its text was not read for this decision; an adaptive delay needs a latency histogram per shard and is left to M6's measurements); choosing the replica by latency or by outstanding calls (more state, for two replicas per shard); tied requests, where the replica that starts the work cancels the other (needs replicas to talk to each other); outlier detection that takes a replica out after calls to it time out (covers the replica that answers pings and not searches, Limits point 2; it needs thresholds that M6's measurements should set); gRPC's client-side health checking (the replica would have to report its own stalls)

## D042 Swaps across replicas: prepare, catch up on demand, keep two versions
- Date: 2026-11-10
- Decision:
  1. A request runs on one version (D031) and each of its shard searches names it (D040), so a replica answers from that version or fails: a response cannot mix versions, whichever versions the replicas hold at the moment. Activation stays the gateway's one atomic store. A replica has no active version
  2. Prepare: once the gateway has loaded and verified a bundle, it sends `Prepare` to every replica of every shard in parallel. The swap goes on when each shard has at least one replica that holds the version; a replica that failed is logged. If a shard has none, the swap is rejected (422) and the active version stays, as for a bundle that fails to load (D031). The first bundle goes the same way, so a gateway does not start while a shard has no replica that can prepare it (as with Valkey, D033 point 6). The calls share `-prepare-timeout` (2 minutes): without a bound, one replica that never answers would keep the swap, and the swap lock, forever
  3. Catch-up: a replica that failed to prepare, was down during the swap, or restarted, which leaves it empty, lacks the index. A search that reaches it gets `FAILED_PRECONDITION`, goes to the next replica at once (D041 point 3), and has the client send that replica a `Prepare` in the background, one at a time per replica and index, within `-prepare-timeout`; after a failure the replica is not asked again for 5 s. The client also sends it the version served each time its connection to the replica comes up (D044). This is the client's own work, as keeping a connection is: it runs for no request, so D029 point 4 does not cover it, and it ends when the client is closed
  4. Retirement: there is no release call. A replica keeps the indexes of two versions; when it has prepared an index of a third, it drops every index of one of the other two: the one that a `Prepare` or a search named longest ago, but never the version served, as the last `Prepare` to name one gave it (D043). A search that is running on a dropped index finishes on it, and the memory goes once the last one has returned, so nothing counts searches in flight
  5. Property 4 over gRPC: two bundles of 2,000 items on two shards of two replicas each, eight workers against 60 swaps, every response equal to the never-swapped in-process pipeline of the version it names. The catalog is far above `VectorTop` on purpose: the gateway scores candidates with its own vectors (D031), so a replica that searched the wrong version shows only in which candidates it returned, and with 40 items every item is a candidate. The broken variant is a replica, made by a server interceptor of the test, that ignores the version a search names and answers from the version it prepared last; the request held across the first swap (D031 point 7) then merges one shard of each version and is caught
  6. Other tests: a swap is rejected while one shard has no replica with the new version and the active version answers 30 requests correctly, then goes through once that shard has one, with a replica of the other shard still lacking it, and the new version answers 30 correctly; a replica given the bundle late holds the index after the searches that found it lacking; a replica restarted on its address, empty, is prepared again while every search is answered correctly; a replica that prepares a third version drops the one named longest ago, counts a `Prepare` as naming, treats two shards of a version as one version, and prepares a dropped version again on request
- Rationale: Two versions are what a swap needs: the active one and the one coming or going. When several gateways swap one after the other, the old and the new version are both named throughout and both stay. Without a release call the gateways need not agree on when a version is unused, and one that stops in the middle of a swap leaves nothing behind that another must clean up. The version, not the index, is the unit of retirement because a replica may hold several shards of one version: counting indexes would drop a shard of the active version to make room for a shard of the next. Preparing on every replica before activation means the first requests on the new version find it built; letting one replica per shard suffice means one replica that is down does not block a swap, and catch-up brings it level without an operator
- Limits: with three versions in use at once, as when one gateway swaps to a third while two others still serve two, the replicas drop one that is in use: its searches fail on every replica of a shard, the responses report `shards_partial`, and catch-up prepares it again at the cost of another; in Kubernetes the swap script keeps the gateways to two versions (D048). A swap that is rejected leaves the new version on the replicas that prepared it, where it has taken the place of the version the gateway does not serve. A replica that restarts holds nothing and accepts connections at once; it is ready only once it holds the version served again (D044). A replica keeps two versions in memory at all times, three while it builds a third, plus the bundle's whole vector file while it loads. A replica that cannot prepare a version, for lack of its directory, is asked again every 5 s for as long as searches reach it, and, for the version served, while the gateway's connection to it is up (D044), and each of those searches costs one failed call before the next replica answers; only the gateway's log shows it. A `Prepare` the gateway gave up on is not cancelled on the replica: the build goes on and its index is held. A replica restarted during a swap's prepare may miss it and is prepared by catch-up. The number of splits and modes held per version is not bounded
- Alternatives: a `Release` call followed by unloading after 30 s without requests or searches in flight (the gateways would have to agree on the last user, and one that stopped before releasing would leave the version loaded); a reference per gateway on each replica (the same, with more state); keeping every version (memory grows with each swap); keeping only the newest once it is prepared (the requests still running on the previous version would lose their shards); requiring every replica to prepare (one replica down would block every swap)

## D043 A Prepare names the version the gateway serves
- Date: 2026-11-10
- Decision:
  1. `PrepareRequest` carries `serving_version`: the bundle version the gateway serves when it sends the request; while it prepares its first bundle, the version it prepares (D044 point 2). The gateway reads it from `recommend.Live`, for the `Prepare` of a swap and for the one that has a replica catch up (D042 point 3)
  2. A replica's version served is the one the last `Prepare` to name one gave, from the moment the request arrives; a `Prepare` that names none leaves it as it was. A replica that holds more than two versions once it has prepared an index does not drop that version; of the others it drops the one named longest ago, as before (D042 point 4), which is never the one just prepared
  3. Tests: at a replica, after a swap to v2 and a late search of v1, preparing v3 with v2 served drops v1, and a version named last gives way to the one served, also when the `Prepare` of a fourth version names none. Through the client, a replica keeps the served version when it prepares a version and when it catches up; with the field left out of either call the test fails (checked once, by hand). Through the binaries, three swaps in a row over three bundles, each prepare followed by a search of the previous version at every replica and no request in between, leave every replica holding the version served; with the gateway not passing its version to the client, a replica lacks it after the second swap (checked once, by hand)
- Rationale: Only the gateway knows which version is in use. A replica that goes by the last naming guesses, and on a quiet gateway it guesses wrong: after a swap to v2, a request still running on v1 names v1 last; if no search of v2 reaches the replica before the next `Prepare`, because the cache answers, the users have no vector or nothing arrives, the replica drops v2, the version served, and keeps v1. A test on the replica as it was showed it: v2 answered `FAILED_PRECONDITION` and v1 was still held. With every replica of a shard in that state the shard is left out (`shards_partial`) until catch-up has rebuilt the index: tens of milliseconds for 25.6k items in exact mode and about a second in HNSW mode (D040, Measured), longer with the catalog. Stating the version in the request makes keeping it a matter of the protocol and not of timing, for one string field, and the API is cheapest to change before M5 deploys it
- Limits: a gateway protects the version it serves in its own requests only. With several gateways, three versions in use at once still push one out (D042, Limits); in Kubernetes the swap script keeps them to two (D048).
- Alternatives: the release call or per-gateway references of D042 (the gateways would have to agree on the last user); the flag on searches (a quiet gateway sends none, which is the failing case); counting a `Prepare` as naming the served version too (the next late search of the previous version undoes it)

## D044 A replica is ready while it holds the version served
- Date: 2026-11-10
- Decision:
  1. A replica is ready while it holds an index of the version served, the one the last `Prepare` to name one gave (D043 point 2). It reports so in `grpc.health.v1`, service "": SERVING then, NOT_SERVING before, while it cannot build that version, and whatever else it holds
  2. The first bundle names itself: a `Prepare` sent while the gateway serves nothing gives the version it prepares as the one served
  3. The client opens a connection to every replica at `Dial` and keeps it open. Every second while a connection is up, it compares the version the gateway serves with the one it last prepared that replica with on this connection; when they differ, it sends the replica a `Prepare` of that version, naming it served, and after a failure waits 5 s before the next. A replica that restarted, was down during a prepare, or could not prepare so becomes ready without a request, within gRPC's reconnect wait (1 s, growing to 5 s), a second and a build; and every replica learns of a swap within a second of its activation, at the cost of one `Prepare` per replica that finds the index held
  4. Five cases. A fresh deployment: no replica is ready until the gateway has prepared its first bundle on it. A replica that restarts: empty and not ready until the gateway's connection to it is back and it has built the version served. A replica down during a swap: once back, it is prepared with whichever version the gateway then serves. A swap: preparing the next version, or failing to, leaves a replica ready on the version served. A replica that cannot build the version served, for lack of its directory: not ready until it can, so a rolling update stops at it
  5. What a deployment must provide (M5, kind): the address the gateway dials for a replica resolves while the replica is not ready (per-Pod DNS names with `publishNotReadyAddresses`), since only the gateway's `Prepare` makes it ready; a readiness probe on `grpc.health.v1`, so that a rolling update takes a shard's next replica only once the previous one is ready again; with several gateways, `minReadySeconds` above the reconnect wait, since the first gateway to reconnect makes the replica ready while the others may still be waiting. When a connection to a replica fails, the gateway looks its name up again at most a second after the last lookup (D041 point 1), so it finds a restarted Pod's new address within its reconnect wait once the name resolves to it
  6. Tests: a replica is not ready before its first `Prepare`, is ready once it holds the version served, stays ready when the next version fails to prepare, is not ready when told it serves a version it cannot build, and is ready again once it can; the version served is kept through a `Prepare` that names none. Through the client: a replica that was down during the prepare and one restarted on its address become ready with no search; the first version prepared makes every replica ready. A replica whose connection stays up follows the version served: it becomes not ready when that turns into a version it cannot build, and ready once it can, with no search. The gateway run in its own process on two replicas, under the race detector, has a restarted replica ready again. Through the binaries: a replica killed and restarted is ready again, holding the active version, with no request; a rolling restart of the four replicas, each one stopped with SIGTERM and the next only once the restarted one is ready, under requests that run throughout, has every response complete and some during each restart. Broken variants, each run once by hand: a replica ready whenever it holds any index; no watching of the connections; watching that acts only when a connection changes state (the replica that follows the version served stays ready on the old one); a first `Prepare` that names no version; a replica ready from its start, which in the rolling restart lets the next replica go before the gateway has reconnected and gives `shards_partial`
- Rationale: The gateway dials each replica's address and picks among them by connection state (D041), so readiness serves the rollout: it must mean that taking the shard's next replica leaves the shard served, and holding the version served is that. A restarted replica that waited for a search to find it lacking (D042) would depend on traffic: with no requests, or all of them answered by the cache, it would never be ready and the rollout would stall. The connection is the gateway's own state and needs no traffic. Readiness as "holds any index" would let a replica that holds only the previous version, after a swap it failed to prepare, pass as ready
- Limits: For up to a second after a swap a replica names the previous version as served, and reports ready on it. A replica that cannot prepare the version served is asked again every 5 s while its connection is up, and only the gateway's log shows it. With several gateways, the version served is whichever named it last (D043, Limits). A connection to every replica is open from the start, also to a replica the gateway never searches. `ClientConn.Connect` is experimental in grpc-go (D041, Limits)
- Alternatives: the gateway watching each replica's `Health.Watch` stream (it would learn readiness, which it does not use, and still have to send the `Prepare`); a `Prepare` of the version served to every replica on a timer, whether it holds it or not (a call per replica per period); acting only when a connection comes up (a replica connected before the first bundle is active, or one whose `Prepare` failed with its connection up, would wait for a search, and with no requests stay not ready); readiness from the replica's own bundle directory, such as the newest version (only the gateway knows which version is served, D043); readiness as holding any index (above)

## D045 Shutdown of the gateway and the replicas
- Date: 2026-11-10
- Decision: this refines the shutdown of D022
  1. annshard, on SIGTERM, reports NOT_SERVING (D044) from then on, closes its listener and sends every connection a GOAWAY, lets the calls in flight finish, ends those still running after `-drain` (10 s), saying so in its log, and exits. There is no wait between the report and the stop
  2. The gateway, on SIGTERM, answers `/readyz` with 503 and goes on answering for `-shutdown-delay`, on new connections and on those already open; while it is not ready, each response closes its connection (`Connection: close`). Then it closes its listeners, gives the requests in flight `-drain`, and closes the rest in the order it always had: the active bundle, the Kafka producer, the shard client, Valkey. `-shutdown-delay` defaults to 0, as kube-apiserver's `--shutdown-delay-duration` does; the manifests set it
  3. Kafka: a 202 from `/v1/events` means the brokers acknowledged every record (D034 point 3), so nothing waits in the producer at shutdown and it is not flushed. The offsets are ingest's, which commits what it applied and leaves the group on SIGTERM (D035)
  4. Tests: a replica told to stop reports NOT_SERVING at once to a health watch in flight, refuses new connections, goes on serving the watch, and stops when the watch ends; with a call that never ends it stops at the drain and not before. The gateway told to stop answers `/readyz` with 503 at once, answers other requests with 200 and `Connection: close` during the delay, also on a connection that was idle at the stop, then refuses connections, and the request in flight finishes. Through the binaries, every replica of the rolling restart (D044 point 6) exits with status 0 within its drain. Broken variants, each run once by hand: a replica that stops at once (the watch is cut before NOT_SERVING arrives); a replica that waits without bound (still serving 10 s after the drain); a gateway without the delay (`/readyz` never answers 503: the listener is closed)
- Rationale: The gateway dials replicas by address and picks among them by connection state (D041), so a replica's readiness tells the gateway nothing and waiting after the report would only slow a rollout. After the GOAWAY the gateway sends no new call on that connection, and a search already on its way when the replica stops fails over to the shard's other replica at once (D041 point 3), with the hedge behind it. On the gateway, Kubernetes removes a terminating Pod's endpoints while it signals the Pod, with no ordering between the two (D022), so the gateway must go on answering until the removal has reached every load balancer. Doing so in the process lets it close connections as it answers, which moves a client that keeps connections open to another instance before the listener closes; the image also needs no shell. Outside Kubernetes nothing removes endpoints, hence the default of 0
- Limits: `-shutdown-delay` must outlast the endpoint removal and `terminationGracePeriodSeconds` the delay plus both drains; both are measured in kind and set there (D047). A `Prepare` running on a replica past its drain is cut, and the swap counts that replica as failed (D042). A call that the gateway sends as the replica's GOAWAY arrives may fail with UNAVAILABLE and goes to the next replica, one retry. A connection that stays idle through the whole delay is closed when the listeners close, and a request a client writes on it at that moment fails
- Alternatives: turning keep-alives off at the stop (Go's server then closes every idle connection at once, while the load balancers still send requests to it, and a request a client writes on one as it closes fails; a POST is not retried); a `preStop` hook with Kubernetes' `sleep` action (no shell needed, but SIGTERM reaches the process only after the hook, so during the wait the gateway answers `/readyz` with 200 and keeps connections open); a wait on the replica between the report and the stop (nothing routes by its readiness); flushing the Kafka producer at shutdown (nothing is pending once a request has its 202)

## D046 A bundle's version is the digest of its files
- Date: 2026-11-10
- Decision:
  1. `model_version` must be the first 12 hex digits of the SHA-256 of every file's name followed by its sha256 from the manifest, in name order, over every file but `manifest.json`: the version `tools/bundle/build.py` has always written. `bundle.Load` and `bundle.Vectors` reject a bundle whose version is another, so the gateway and every replica do; `tools/bundle/verify.py` applies the same rule. SPEC §8 states it, and seqrec-lab's export (M7) must follow it
  2. No change to the shard API: a replica given a bundle under a version's name now holds the files the version names, as the gateway does, so a `Prepare` need not carry the checksum of `items.npy`
  3. Tests: `Load` and `Vectors` reject a bundle whose version is not its files'; a replica refuses to prepare a version whose directory holds other vectors listed with their own checksum. The test bundles take the version their files give
- Rationale: D031 point 5 and D040 relied on the version naming the content, and the loader trusted the manifest for it. A bundle copied under another's directory name, or a manifest edited by hand, was served as that version: by a replica, with candidates from other vectors; by the gateway, with cache entries of another content. The digest was already in every bundle the project builds, so checking it costs one hash over the manifest and changes no version (5de55036a382 and 9fb3c7e84140 rebuilt the same)
- Limits: the digest covers the files, not the manifest's own fields: two bundles whose files are equal and whose `train_cutoff_ts`, `max_seq_len` or build parameters differ have one version. This matters to the gateway (D030's key) and not to a replica, which reads `items.npy` only and checks `item_count` and `dim` against its shape. Twelve hex digits are 48 bits: enough against a bundle put in the wrong place, not against one made to collide, which the unauthenticated shard API (D040) does not guard against either
- Alternatives: the sha256 of `items.npy` in `PrepareRequest` (a proto change that covers the replicas only, and leaves the gateway trusting the manifest); the full 64 digits (every version recorded so far would change)

## D047 Deployment on Kubernetes, checked in kind
- Date: 2026-11-11
- Decision:
  1. Images: `Dockerfile` builds one per command on distroless, as the nonroot user, with base images pinned by digest. The gateway and annshard link ONNX Runtime's Go binding, which needs cgo: the gateway runs on `cc` (glibc and libstdc++) with ONNX Runtime 1.31.1's release library at `/usr/local/lib`, added by checksum; annshard on `base`, since it never loads ONNX Runtime; ingest is static. Compressed, the gateway's is about 31 MB and annshard's 14 MB
  2. `deploy/kind` (kustomize) deploys into the namespace `recserve`, where Pod Security `restricted` is enforced: every container runs as a non-root user, on a read-only root file system, with no capabilities and the runtime's seccomp profile. Bundles and splits are on one read-only volume (D048), in kind the node's `/data`, which is the host's DATA
  3. Replicas: a StatefulSet of four Pods, which `-shard-addrs` names as two shards of two, behind a headless Service with `publishNotReadyAddresses` (D044 point 5); `podManagementPolicy: Parallel`; readiness by the gRPC probe on `grpc.health.v1` every second, liveness by a TCP connection, since the health service reports NOT_SERVING until a gateway has prepared the replica; `minReadySeconds: 10`; `terminationGracePeriodSeconds: 15`, the drain (10 s) and the exit
  4. Gateways: a Deployment of three, rolled with `maxSurge: 1` and `maxUnavailable: 0`, and an HPA from three to four at 70% CPU on metrics-server v0.9.1 (D022). `-shutdown-delay 5s`, `-drain 10s`, `terminationGracePeriodSeconds: 20`. A startup probe on `/livez` allows 150 s, past `-prepare-timeout`, since the listener opens once the first bundle is prepared; readiness on `/readyz` every 2 s; liveness on `/livez`. A NodePort, published on the host's loopback
  5. Resources, requests then limits: a gateway 250m CPU and 384 Mi, 2 CPUs and 512 Mi; a replica 100m and 64 Mi, 1 CPU and 128 Mi
  6. In kind the gateways' stage budgets are 100 ms, where SPEC §5 has 3 to 15 ms: kind checks behavior, not latency (D022)
  7. `make kind-up` creates the cluster, loads the images, deploys, and prints how long the Pods took to be ready and how often the gateways restarted; `make kind-swap` swaps (D048); `make kind-down` deletes the cluster. The cluster's configuration has two patches that let kind run on a host with cgroup v1 or without `CAP_SYS_RESOURCE`; elsewhere they change nothing
  8. Zero-error check (`make kind-check`, SPEC §10): loadgen offers 100 requests/s through the NodePort while the gateways roll, then the replicas, then the gateways swap bundles, from the mean encoder's to one with the ONNX encoder and the ranker (`make bundle ENCODER=onnx RANKER=1`), so that the image's ONNX Runtime runs both: a ranker that failed would degrade the responses. With the admission limits of D050 on, 15,000 of 15,000 responses passed, 6,359 from 5de55036a382 and 8,641 from b7ff0634dd7b, in 2 min 36 s. Every response must be a recommendation with nothing degraded, and both versions must answer. Not in CI: it needs the real data and two bundles. Broken variants, each run once: without the resolver setting of D041 point 1, 815 of 15,000 responses were degraded; with `-shutdown-delay 0`, 56 failed with a connection reset; with `publishNotReadyAddresses: false`, no replica was ready and every gateway was in CrashLoopBackOff after 90 s
  9. Only the gateway Pods of the namespace reach the replicas' port, by a NetworkPolicy (D040). `scripts/kind-netpol.sh` (`make kind-netpol`) checks that it is enforced: a gateway Pod reaches the port, through an ephemeral container in its network namespace; a Pod of the namespace with other labels does not, nor a Pod with the gateway's labels in another namespace. The CI deploy job runs it in kind, on a cluster whose gateways cannot start for lack of a bundle, since the replicas need none to listen. kindnet enforces NetworkPolicy with kube-network-policies, which sends each new connection through nftables' queue expression to a verdict in user space; on a kernel without that expression nothing is enforced and the check fails, as it does on the development host: the broken variant. The check also requires the kubelet's probes to reach the replica through the policy: the replica is ready, or its readiness probe answered NOT_SERVING
- Measured (kind v0.33, Kubernetes 1.37, one node of 4 CPUs with cgroup v1, kube-proxy in iptables mode, images loaded):
  1. Endpoint removal: kube-proxy's rules stopped sending to a deleted gateway Pod 0.14 to 0.93 s after the delete, in 10 deletions; the Pod was gone after 5.8 to 6.2 s, the delay and 0.8 s to close
  2. First deployment, from the apply until every Pod was ready: 17.7 s on a new cluster, no gateway restarted; 3.9 and 4.6 s on a cluster that had run it, every gateway restarted once, since its replicas' names did not resolve yet. With the replicas applied 30, 60 and 120 s after the gateways: 10.5 and 11.4, 29.5, and 61.4 s from the replicas' apply, with 3, 4 and 5 restarts. With `OrderedReady`: 45.5 s twice, 3 restarts each
  3. Load: at 100 requests/s over three gateways, a gateway used at most 138m CPU and 303 Mi, a replica 62m and 35 Mi. With SPEC §5's budgets, 3 of 24,000 responses timed out with no rollout at all, the slowest taking 22 ms, and 2 to 5 in each of three runs of the check; none of them was a failure
  4. The check: the gateways rolled in 9 to 11 s, the replicas in 38 to 40 s, a swap in 15 to 17 s
- Measured in M6 (docs/BENCHMARKS.md, M6, kind): with SPEC §5's budgets instead of 100 ms, three runs of `kind-check`'s rollouts and swap had no error, and at most 0.133% of a phase's responses degraded (four responses in all); p99 was at most 9.91 ms, during the gateways' rollout. The check keeps 100 ms, since the control plane shares the CPUs (D022)
- Rationale: The gateway dials each replica by a name that must stay with it across restarts, which a StatefulSet's Pods have and a Deployment's do not. A replica is ready once a gateway has prepared it, and a gateway starts once every shard has a replica that prepares (D042 point 2), so with `OrderedReady` each next replica is created only after a gateway's restart. `minReadySeconds` covers a gateway whose reconnect wait has grown to its 5 s cap while the replica was down, plus a lookup (D041 point 1) and a connection; in kind the gateways reached a restarted replica about when it turned ready, and 0 also passed the check. The shutdown delay is five times the slowest removal measured, and the grace period the delay, the drain, the time to close and a margin. 100 ms is five times the slowest response with no rollout: SPEC §5's budgets turn the node's CPU contention, among the control plane, the Pods and the load generator, into timeouts, and a degraded response must mean a failure; a longer budget, such as 1 s, would also hide a search waiting for a connection. The HPA's minimum of three gives the check several gateways (D044 point 5), and its maximum fits the node. Memory requests are above the peaks measured, limits about one and a half to four times them
- Limits: The manifests check the properties between the gateways and the replicas. The gateways keep histories in the process (`-preload`); a production deployment also needs Valkey, Kafka and ingest, with manifests of their own, which compose has. One node: no anti-affinity and no PodDisruptionBudget, and the figures include the control plane's CPU use (D022). A gateway that cannot prepare its first bundle exits (D042 point 2) and the kubelet restarts it after a wait that doubles from 10 s up to 5 minutes, its default (Kubernetes 1.37, with `ReduceDefaultCrashLoopBackOffDecay` off), so replicas that come long after the gateways wait for the gateways' current wait: applied together, the Pods were ready 3.9 and 4.6 s after the apply, with one restart per gateway; with the replicas 30, 60 and 120 s late, 10.5 and 11.4 s, 29.5 s and 61.4 s after the replicas' apply, with 3, 4 and 5 restarts; at most 5 minutes in any case. The shutdown delay rests on kube-proxy on the same node; behind an external load balancer the removal takes longer and must be measured there. With the budgets of the kind manifests the check does not see what rollouts do to latency, which is M6's to measure; the first requests of a new gateway took longer than 15 ms. A grace period below the delay also passed the check: early in the delay every keep-alive connection closes after a response and moves, so what is left to cut is rare; the value follows from the sum. The NetworkPolicy is enforced only where the kernel has nftables' queue expression; the development host has neither it nor the iptables set match that Calico would use, so only CI checks it. The policy admits any Pod of the namespace with the gateway's label, and traffic from the node, which includes Pods on the host's network in namespaces without Pod Security; `make kind-netpol` leaves its ephemeral container in a gateway Pod. `podManagementPolicy: Parallel` keeps a rolling update from taking a replica while another is unready only with `MaxUnavailableStatefulSet`, on by default in 1.37; without it the update checks only the Pods it has replaced. Applying the manifests again sets the gateways back to three, even while the HPA holds four. Deleting the namespace leaves the PersistentVolume released and bound to the old claim, so a new apply waits for good: `make kind-down` resets. The alert rule sees failures that another replica makes up for (D041), not a replica that is down, which no search reaches. The images and the scripts are for linux/amd64
- Alternatives: a Deployment with a Service per replica (one name per Service, with whichever Pod carries its label); a `preStop` sleep (D045); an init container that waits for the replicas' names (it needs a shell image, and the restart does the same); Helm (one environment); SPEC §5's budgets in the check (it would fail on timeouts unrelated to a rollout)

## D048 Swaps across several gateways
- Date: 2026-11-11
- Decision:
  1. Bundles are on one read-only volume that every gateway and replica mounts, a directory per version. A version is published by writing its directory there before it is swapped to: a replica finds it under `-bundles` when a gateway has it prepared (D042)
  2. In Kubernetes a swap is a rollout of the gateway Deployment to another `BUNDLE_VERSION`. A new Pod loads the bundle and has the replicas prepare it before it is ready, as at any start (D042 point 2); an old one serves its version until it is replaced, then through its shutdown delay and drain (D045). The Deployment's template is the one record of the version served, so Pods that the HPA adds or that restart start on it. The admin API's swap is not used there: it would leave the template behind, and the next Pod would start on the old version
  3. At most two versions in use. During a rollout only the old and the new ReplicaSet have Pods, but a rollout started before the previous one has ended scales both older ones down at once, which is three versions. `scripts/kind-swap.sh VERSION` (`make kind-swap`) starts only when every gateway Pod, terminating ones included, runs the template's version; it changes the version with a JSON patch whose `test` holds the version it read, so of two swaps started together one fails; and it returns once no Pod runs the previous version
  4. With compose or processes the swap stays the admin API's, hot (D031, D042, D043); with several gateways, one after another, each once the previous has answered, which it does once the previous bundle is closed
  5. Tests: a swap started during another is refused while the first completes; without the check and the `test`, the second goes through (checked once, by hand). The zero-error check swaps under load (D047)
- Rationale: The replicas must see a version before any gateway serves it, and should not restart for it. An init container that copies the bundle into an emptyDir (KServe's storage initializer), a bundle in the image, or a bundle as an image volume each show a version only to a Pod started after it: every swap would roll the replicas, and retiring a version roll them again. A shared volume read by path is how Triton's model repository is served. A rollout as the swap keeps the version in the object that Kubernetes reconciles, so scaling and restarts follow it with nothing outside watching
- Limits: A swap costs a rollout: each gateway loads the bundle, preloads the histories (D047) and starts with an empty cache. `kubectl apply` of the manifests sets the manifest's version, so after a swap it swaps back without the script's check. A version's directory must stay on the volume while a gateway may start on it, a rollback included; nothing deletes old ones. A version the new gateways cannot load, for a file their user cannot read or a failed check, leaves them restarting while the old ones serve; the script gives up after 10 minutes, and since two versions then have Pods it refuses every swap until `kubectl rollout undo` ends the rollout. In kind the volume is a host directory; a cluster of several nodes needs a ReadOnlyMany network volume
- Alternatives: the admin API's swap on every Pod in turn, through a port-forward (the template still names the old version); an image volume per version (above); the version in a ConfigMap read at start (a change starts no rollout, so the Pods serve different versions until each restarts)

## D049 A/B arms rank or keep retrieval order within one bundle
- Date: 2026-11-11
- Decision:
  1. An arm differs from another only in how it orders the candidates: `ranker`, by the bundle's ranker, or `retrieval`, by retrieval score without running the ranker. Every arm serves the active bundle, so swaps, the replicas' versions and the cache's version key are as before (D031, D042, D048)
  2. `-experiment NAME -arms control=retrieval:50,treatment=ranker:50`: arms as name=mode:weight, weights in whole percent summing to 100. A user's bucket is the first 8 bytes of the SHA-256 of NAME, ".", the user ID, as a big-endian unsigned integer, mod 10,000; the arms take consecutive buckets in the order listed, 100 per percent. Without `-experiment` every request is in the arm `default`, mode `ranker`. A bad specification stops the gateway at start
  3. The gateway assigns the arm after parsing the request and before the pipeline (SPEC §5, first row). The response names the arm and, in `ranking`, what ordered its items: `ranker` only if the ranker scored them; `retrieval` when the arm does not rank, the bundle has no ranker, or the ranker timed out or failed. So an arm that asks for a ranker the bundle lacks is visible in every response and exposure, not only in the log at start
  4. The arm's name and mode are in the result cache key (D030): gateways that share the cache on Valkey may run different experiments, as during the rollout that changes one
  5. `-exposure-log` writes a JSON line to stdout for every answered recommend request, cache hits and degraded responses included: `time`, `user_id`, `ts`, `experiment`, `arm`, `ranking`, `model_version`, `items` (IDs, in order), `degraded`, `cached` (SPEC §6). The service's own log stays on stderr. A request only queues its line, for one writer goroutine; a full queue (4,096 lines) drops the line and counts it in `recserve_exposures_dropped_total`, as does a failed write. `recserve_arm_requests_total{arm, ranking}` counts answered requests
  6. Property 3 (SPEC §7): golden buckets computed with `sha256sum`, outside Go; a chi-square over 100 equal bucket ranges of 1M IDs below the 0.999 quantile (148.23); each arm's share of those IDs within 0.003 of a 10/30/60 split. The broken variant hashes with a seed drawn by the process (`hash/maphash`): uniform and split as configured, it fails the golden buckets. The cache key test computes one user's response in both arms, then hits each; with the arm left out of the key, the second arm is served the first's response (checked once, by hand). The exposure test sends an arm that asks for the ranker to a bundle without one, and requires `ranking: retrieval` in the response and in the line
- Rationale: The ranker this milestone adds is what the first experiment compares with retrieval order, and the arms need nothing that the swap semantics do not already give. Hashing an experiment key with the user ID into 10,000 buckets that the arms split by cumulative weight is how Statsig (SHA-256, first 8 bytes), GrowthBook (FNV-1a) and Optimizely (MurmurHash3) assign; SHA-256 is in the standard library and in every warehouse's SQL. Warehouses usually join exposure logs rather than recompute assignments, so the log is the record and the formula is there to check it. stdout keeps the exposures apart from the service's log for the cluster's log collection, with no new dependency; the queue keeps a slow collector from holding up requests
- Limits: Changing the experiment's name or arms reassigns users; a rollout that changes it serves both configurations until it ends, and a user may see both. Exposures are lost when the queue is full, when stdout fails, and those still queued when the process is killed; a stdout whose reader has closed it ends the process with SIGPIPE, as it would through the service's log on stderr, rather than counting the line; at shutdown the gateway writes the queue after the drain, and waits for stdout as long as it blocks. There is no override to put a given user in an arm, and no layering of experiments: one experiment at a time per gateway. The split is checked by the property test and the arm metric; the statistics of an experiment's results are left to the warehouse
- Alternatives: several rankers in one bundle, an arm choosing one (a change to the bundle contract and its load check, and there is one ranker); a bundle version per arm (two versions in use at all times and a third during any swap, which the replicas' two-version retirement (D042) and the swap script (D048) do not allow); a warning at start when an arm asks for a missing ranker (the responses would still read as that arm's treatment); exposures to Kafka (durable, but a dependency the gateway runs without)

## D050 Admission limits on recommend requests
- Date: 2026-11-11
- Decision:
  1. Two limits guard `POST /v1/recommend`, each off at 0, the binary's default: `-max-rate`, a token bucket (`golang.org/x/time/rate`) with a burst of one second's worth, and `-max-inflight`, the requests served at a time, a buffered channel taken without waiting. The rate is checked before the request's body is read, the in-flight slot taken once it has been read, so a client that holds back its body holds no slot. A request over either is answered 503 with `Retry-After: 1`, counted in `recserve_shed_total{reason}` (`rate`, `inflight`) and in `recserve_http_requests_total` with its code. Nothing queues
  2. The probes, `/metrics`, `/v1/events` and the admin API are not limited, and readiness does not follow load: `/readyz` stays 200 while requests are turned away (D045 unchanged)
  3. The replicas have no limit of their own: only the gateways reach them (D047), and an admitted request makes at most one search per shard plus its hedges, which have their own budget (D041)
  4. In kind, `-max-rate 400` and `-max-inflight 64` per gateway. At 100 requests/s over three gateways a gateway used at most 138m CPU (D047), so at most 4.1 ms of CPU per request if the load was even, less if not; the 2-CPU limit then serves about 480 requests/s, and 400 is about 80% of it. 400/s over SPEC §5's 50 ms is 20 requests in flight; 64 leaves room for bursts and still bounds the work when a stage stalls. The zero-error check offers 100/s, a quarter of one gateway's rate even if every request reaches the same gateway. compose sets no limits, for M6's sweeps
  5. Tests: with three requests held in the pipeline by a history store that does not answer, a fourth is answered 503 with `Retry-After` within a second, while the probes, `/metrics` and `/v1/events` answer, and the three answer 200 once released; the broken variant queues for a slot, and the fourth and the probes time out. A client that sends its headers and holds back its body leaves the only slot to the next request. At 5/s on a fixed clock, five requests pass, the sixth is turned away, and one passes 200 ms later
- Rationale: The two limits stop different things: the rate stops more arrivals than the gateway is provisioned for; the in-flight limit stops work from piling up when the path slows down while arrivals stay within the rate, as when a dependency is slow but within its budget. Turning away at once keeps the admitted requests within their budgets: a queue at the door spends the budget before the work starts (SRE book, Handling Overload: 503 over an in-flight limit, small bounded queues). Readiness that failed under load would take every gateway out at once, the cascading failure the same chapter warns of. Defaults of 0 because the right values follow from the CPU an instance gets: a fixed default would either turn healthy load away or protect nothing, and M6's sweeps must reach saturation
- Limits: The limits are per gateway: a client spread over N gateways is allowed N times the rate, and an HPA that adds a gateway adds its rate. The values in kind rest on one measurement at 100 requests/s, not on a capacity sweep (M6). In the zero-error check loadgen keeps 64 connections with a request each at most, so the in-flight limit of 64 cannot trip there, with no margin; the rate trips only if loadgen's catch-up after a stall of about 4 s lands mostly on one gateway. `/v1/events` is bounded only by `-events-timeout` and its body size. A client that ignores `Retry-After` and retries at once is turned away again, and each attempt costs the gateway a little
- Alternatives: queueing with a deadline (the waiting spends the budget, and a full queue still turns away); an adaptive concurrency limit, as Netflix's concurrency-limits (a control loop to tune and test, before M6 has measured capacity); failing readiness under load (above); per-client limits (clients are not authenticated, D040); a gRPC `InTapHandle` limit on the replicas (point 3)
- Updated in M6 (docs/BENCHMARKS.md, M6): from the gateway's CPU per request at the headline, 550 requests/s in compose, 1.098 ms in the run with the median p99 (1.098 to 1.199 ms in the three), a gateway's capacity on 2 CPUs is estimated at 2/c = 1,821 requests/s; in kind `-max-rate` becomes 1,450 and `-max-inflight` 152. The estimate rests on one quantity measured while the gateway shared three CPUs with the replicas, Valkey and Kafka; a gateway with its histories in the process, as in kind, may use less CPU per request

## D051 OpenTelemetry tracing, Jaeger in compose
- Date: 2026-11-11
- Decision:
  1. Tracing is on when the standard environment names an OTLP endpoint, `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, and configured by the same environment: the sampler (`OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG`; parent-based and always on by default) and the service name (`OTEL_SERVICE_NAME`, else `gateway` or `annshard`). No flags. `internal/tracing` installs the SDK's tracer provider with a batch span processor and the OTLP gRPC exporter (`go.opentelemetry.io/otel` v1.47.0), and W3C trace context propagation
  2. When on: the gateway traces `/v1/recommend` and `/v1/events` (otelhttp v0.72.0), a span each named by method and path; the probes and `/metrics` make none. The replica client and server trace their calls (otelgrpc v0.72.0), the server leaving out health checks, which the kubelet sends every second. Within a request the pipeline makes a span per stage: `history`, `cache` (the read), `encoder`, `retrieval`, whose children are the shard searches' calls, a hedge's included, and `ranker`. The request's span carries `recserve.arm`, `recserve.ranking`, `recserve.model_version`, `recserve.cached` and `recserve.degraded`. The client's background calls (catch-up and prepare on connect, D042, D044) make traces of their own
  3. When off nothing is installed: the HTTP handler and the gRPC options are as before, and the stage spans go to the global no-op tracer, a call that returns its context with a span that records nothing
  4. Nothing on the request path waits for the collector. The exporter connects in the background; the batch processor queues 2,048 spans and drops what does not fit, never blocking a span's end; an export that fails is retried in the background within the exporter's 10 s timeout, then its spans are dropped; failures are logged through the service's log. At exit, after the drain, the spans left are exported within 2 s (`tracing.FlushTimeout`): the gateway's grace period in kind, 20 s, covers the delay, the drain and this
  5. Sampling is decided at the gateway, or by a client that sends a `traceparent`, which the gateway takes as the parent; the replicas follow the parent's decision, so a trace holds all of its request's spans or none. compose samples every request, for development; a production deployment would set `parentbased_traceidratio`, about 1% at the gateways' rates
  6. compose's `app` profile runs Jaeger 2.23.0 all-in-one (spans in memory), pinned by digest; the gateway and the replicas export to it over OTLP gRPC on the compose network, and its UI is on the host's loopback at 16686. kind runs without it
  7. Test: a gateway and two replicas wired as the commands wire them, with a span recorder as the provider, installed once for the package's tests, since tracers taken before a provider is set stay with the first: the replicas' search spans are in the request's trace, each below a client call below `retrieval` below the request's span, the history and encoder spans are below the request's span, the request's span carries the arm, ranking and version, and the probe makes no span. The broken variant builds the instrumentation with no propagator, the global default: the replicas' spans start traces of their own
- Rationale: The standard variables are how every OpenTelemetry SDK and collector is configured, so a deployment points the services at its collector without knowing their flags. Head sampling at the gateway with parent-based replicas is the SDK's default and keeps traces whole. Spans per stage show where a request spent its budget, which the stage budgets of D029 make the first question about a slow or degraded response; the Valkey and Kafka clients' own instrumentation would be further dependencies, and the history and cache spans already time their calls. Leaving the instrumentation out when off, rather than running it against a no-op provider, keeps the request path of a gateway without a collector as it was
- Limits: The cost when on is not measured: per sampled request about ten spans are recorded and exported in the background, and their CPU counts in SPEC §5's other overhead; M6's sweeps run without tracing. Spans dropped for a full queue or a collector that is down are not counted by the service. A client can force or suppress sampling with its own `traceparent` (`otelhttp.WithPublicEndpoint` would make it a link instead). Valkey and Kafka calls have no spans of their own; the events consumer (ingest) is not traced. Jaeger keeps spans in memory, and loses them when it restarts
- Alternatives: flags for the endpoint and sampler (the standard environment does it); the instrumentation always installed against a no-op provider (a cost on every request without a collector); tail sampling in a collector (a component to run; head sampling suffices to see a request whole); the OTLP HTTP exporter (gRPC is already in both binaries)

## D053 vec.Dot in AVX2, summed in a fixed order
- Date: 2026-11-11
- Decision: `vec.Dot`, the float64 inner product of exact search, the ranker's features and the vector score, adds its products in one fixed order: 16 partial sums over the full blocks of 16 elements, sum l taking element 16i + l, the first four also over a last block of 4; then per lane l of four, (s_l + s_4+l) + (s_8+l + s_12+l); then the lanes as (l0 + l2) + (l1 + l3); then the elements left one at a time. On amd64 with AVX2 and FMA (`golang.org/x/sys/cpu`) hand-written assembly runs it, converting four float32 values at a time to float64 and adding their products with FMA; elsewhere Go code does the same additions. A product of two float32 values is exact in float64, so the fused and the separate multiply-add round alike, and the two give the same result to the bit
- Rationale: The CPU profile at 400 requests/s (docs/BENCHMARKS.md, M6) had `vec.Dot` at 54% of a replica's CPU and 9% of the gateway's, with the replicas together using more CPU per request than the gateway. The fixed order is the one the vector unit computes fastest; defining it, rather than the assembly, keeps one result on every CPU
- Results: the order differs from the previous one, a sum from first to last element, so a result can differ from before in the last bits, about 1e-16 relative. Bundle golden cases are checked to 1e-6, and exact search orders two items differently only if their scores were equal to that precision. No committed file depends on those bits: the tests pass unchanged, and the result files of docs/BENCHMARKS.md hold recalls and latencies, not scores
- Tests: `Dot`, the Go code and the assembly all equal the definition written out element by element, to the bit, for lengths 0 to 300 and in a fuzz test; special values (overflow, subnormals, infinities, NaN) agree; the error is within n · 2^-53 times the sum of the products' magnitudes. The assembly with the lanes added in another order fails the first test
- Alternatives: `vec.Dot32`, the float32 product the TASKS candidate named (HNSW only; exact search, the default, does not call it); float32 accumulation in exact search (changes its results beyond the last bits); `GOEXPERIMENT=simd` (an experiment, needed by every build); avo to generate the assembly (a tool dependency for 60 lines)

## D055 vec.Dot32 in AVX, summed in a fixed order
- Date: 2026-11-11
- Decision: `vec.Dot32`, the float32 inner product of the HNSW index and of MMR's cosine, rounds each product to float32 and adds the products in one fixed order: 32 partial sums over the full blocks of 32 elements, sum l taking element 32i + l, the first 8 also over the last blocks of 8; then per lane l of 8, (s_l + s_8+l) + (s_16+l + s_24+l); then the lanes as ((l0 + l4) + (l2 + l6)) + ((l1 + l5) + (l3 + l7)); then the elements left one at a time. On amd64 with AVX2 and FMA (D053's check) hand-written assembly runs it, eight products at a time, with the multiply and the add as separate instructions; elsewhere Go code does the same operations, converting each product to float32 so that the compiler cannot fuse it with the addition. The two give the same result to the bit
- Rationale: annbench's CPU profile on glove (M = 16, ef 400; docs/BENCHMARKS.md, M6) had `Dot32` first, at 76% of the CPU, the condition TASKS set for this change. A product of two float32 values is not exact in float32, so unlike D053 a fused multiply-add would round differently from a multiply and an add; keeping them apart is what lets the Go code match the assembly on every CPU
- Results: the order differs from the previous one, four partial sums over blocks of 4, so a result can differ from before in the last bits, within n · 2^-24 of the sum of the products' magnitudes. HNSW search can then break near ties between candidates differently; on one glove graph file, recall@100 before and after is compared at each ef (docs/BENCHMARKS.md). Golden cases and ranker features use `Dot`, not `Dot32`. On CPUs without AVX2 the Go code with 32 sums may run slower than the four scalar sums it replaces; not measured, since every machine here has AVX2
- Tests: `Dot32`, the Go code and the assembly all equal the definition written out element by element, to the bit, for lengths 0 to 300 and in a fuzz test; special values (overflow, underflow, infinities, NaN) agree; the error is within γ_n = n u / (1 - n u), u = 2^-24, times the sum of the products' magnitudes. The assembly with the four accumulators added in another order fails the first test
- Alternatives: FMA in the assembly (one instruction fewer per block of 8, but Go has no float32 fused multiply-add, and doing it in float64 rounds twice, so the Go code could not match it to the bit); float64 accumulation, as `Dot` (exact products, but half the lanes per instruction; HNSW needs only the order of distances); `GOEXPERIMENT=simd` and avo, as in D053
